## Goal

Build our own deterministic, device-independent, auditable read of the runner's **current condition** (fresh, fatigued, ramping, detraining) — an acute/chronic/balance model computed from the now-comparable per-activity `effort_score` (#186) — and let the coach reason over it. The model is the **EWMA fitness/fatigue/form** shape that Strava Fitness/Freshness and Garmin Training Load implement, so it answers the north-star's origin ask and validates against the platform numbers, while staying ours (platform numbers are validation-only, never the source of truth and never a cold-start seed). It is a tier-3 deterministic durable fact under `Authority tiering`: it grounds the coach's readiness judgment but never overrides this run's measured data or the safety floor.

## Deliverables

1. **The readiness domain module** (`backend/app/services/readiness.py`, a neutral top-level service parallel to the #209 `services/training_load.py`, **not** inside `services/coach/`, so both the coach context builder and a read path call it without reaching into the coach package). Pure math, no LLM, no I/O in the compute:
   - `compute_readiness(daily_loads, *, as_of) -> ReadinessModel`: the EWMA over a daily load series. **fitness** (chronic load EWMA, time constant `FITNESS_TC_DAYS = 42`), **fatigue** (acute load EWMA, `FATIGUE_TC_DAYS = 7`), **form** = fitness − fatigue, **ramp_rate** = fitness change over the last 7 days. Per-day decay `exp(-1/tc)`. The series is EWMA-**seeded** at the window start (seed both averages with the window's mean daily load) so a bounded window reproduces the all-history value and per-read cost stays flat (#167).
   - A `condition` label from documented, owner-tunable **form bands** (e.g. fresh / balanced / fatigued / overreaching) plus a `detraining` read when fitness trends down, and a `warming_up` flag + `confidence` when history is shorter than the chronic window or `sample_count` is below a floor (then the condition label degrades to a low-confidence "building baseline" read rather than a confident verdict).
   - `build_readiness(db, user_id, as_of_date) -> ReadinessModel`: queries the user's non-deleted activities within `READINESS_WINDOW_DAYS = 182` (the M2 baseline window length) up to `as_of_date`, expands them to a daily load series (summing same-day `effort_score`, zero-filling rest days), and calls `compute_readiness`. Guarded so a readiness failure never breaks the caller (the `recompute_runner_baseline` precedent).
   - The exact form-band thresholds, ramp-rate alarm threshold, and warming-up floor are documented module constants, banked here as reversible build choices.

2. **The `training_load` pack section** (`backend/app/services/coach/context.py` + a context schema). `_build_training_load_context(db, activity, prompt_id) -> Optional[TrainingLoadContext]`, gathered inside `build_context_pack` like `_build_calibration_context`, emitting the section **only** under `is_training_load_prompt(prompt_id)` (the `corpus`/`stance`/`block` Optional-and-drop idiom, so the pack stays byte-stable elsewhere). Computed **as of the activity's `start_date`** (so the read includes today's just-analyzed run in the acute load, and a regen of an old activity reproduces the condition as of *then*, not today). Carries fitness/fatigue/form/ramp/condition/trend/warming_up/confidence. The run's `DerivedMetric` / facts are untouched. **No `service.py` resolve step** (unlike voice/stance, which are runner declarations resolved in `service.py`) — readiness is derived from the DB, so it is gathered entirely inside `context.py`.

3. **Prompt composition** (`backend/app/services/coach/prompts.py`): a new two-stage prompt id **`coach_message_v6`** = `coach_message_v5` + a static readiness addendum (the `Vn = V(n-1) + addendum` idiom; existing versions byte-stable), composed for **both opener and fuller modes**. The addendum is **prompt rule 27**: use the `training_load` section to contextualize today's run within the training arc (fitness built, fatigue carried, form/freshness, ramp); it never overrides this run's re-derived `DerivedMetric`, never reads a negative form or an aggressive ramp as an overtraining or medical verdict (the safety floor; continuity with rule 22's load≠intensity), and is set aside while the read reports itself `warming_up`. A new `TRAINING_LOAD_PROMPT_IDS = {coach_message_v6}` gates both the pack section and the addendum; `coach_message_v6` joins `TWO_STAGE_PROMPT_IDS`, `VOICE_PROMPT_IDS`, `CORPUS_PROMPT_IDS`, and `STANCE_PROMPT_IDS` (v6 inherits all of v5's awareness). `is_training_load_prompt(prompt_id)` added. Schema stays 2.0 (the `coach_message_*` family prefix already resolves via `SCHEMA_VERSION_BY_FAMILY`; no schema change).

4. **Read path for the frontend** (`backend/app/api/activities.py` + `backend/app/schemas/detail.py`): project readiness into `ActivityDetailRead.training_load` at read time (the `laps` precedent, #208 — no new endpoint, no new route), computed as of the activity's date via `build_readiness`. The detail page already fetches this payload, so the card renders from the existing fetch.

5. **Frontend readiness card** (`frontend/components/`, `frontend/app/activity/[id]/page.tsx`, `frontend/lib/types/`): a `TrainingLoadCard` panel on the activity detail page, beside the coach report, showing fitness / fatigue / form + the condition label, and an honest low-confidence state when `warming_up`. Types in `frontend/lib/types/`. **UX/taste is owner judgement** — surfaced, not asserted.

6. **Activation + config**: the readiness era arrives by setting `COACH_PROMPT_ID=coach_message_v6`; rollback to any other id is a pure config flip with zero code change. The **repo config default stays `coach_report_v10`**. Per the P1.3 precedent, P3 includes performing the prod flip as part of the milestone: the slow/worst-case generation path is verified before the flip (the P1.1 activation lesson), the #273 delete-then-generate regen race is respected (no regenerate until the worker redeploy is fully complete), the exact Railway var change + rollback line are prepared, and the **flip itself is owner-authorized and owner-executed**; the live path is confirmed after.

## Acceptance criteria

- **AC1**: Under a non-readiness prompt (`coach_message_v5` and earlier), the context pack and coach output are byte-identical to today — the `training_load` section is emitted only under a training-load-aware prompt id, and `readiness.py` / rule 27 are inert.
- **AC2**: Under `coach_message_v6`, the pack carries a `training_load` section with fitness/fatigue/form/ramp/condition/warming_up; the run's `DerivedMetric` / facts are unchanged.
- **AC3** (the load-bearing test): **floor + fact invariance** — the same flagged activity, run with the `training_load` section present vs absent and across condition states (fresh / fatigued / overreaching / warming-up), produces identical surfaced safety flags and an identical `validate_message_policy` outcome; only framing differs. (The `Authority tiering` gate, mirroring `test_corpus_invariance.py`.)
- **AC4** (the correctness oracle): `compute_readiness` matches a hand-computed EWMA over a known synthetic daily-load series (fitness/fatigue/form to the documented rounding); seeding, condition bands, ramp, and the warming-up floor each verified on a fixture. Validated additionally — but only as a cross-check, never as the oracle — against Strava Fitness/Freshness directionally on the real seed.
- **AC5**: **warming-up abstention** — a runner whose history is shorter than the chronic window yields `warming_up=True`, and the coach abstains from a confident condition verdict rather than guessing.
- **AC6**: **read-time, as-of correctness** — readiness for activity X is computed as of X's `start_date` (X is in the acute load); per-read cost stays flat as history grows (the windowed scan; #167). `aiw-performance-profiling` confirms the scan is bounded.
- **AC7**: **activation/rollback** — flipping `COACH_PROMPT_ID` off `coach_message_v6` serves the prior path with zero code change; `coach_message_v1`..`v5` and the `coach_report_v*` chain stay byte-stable; v6 reports legitimately regenerate (new section).
- **AC8**: the readiness card renders fitness/fatigue/form + condition on the activity detail page and an honest low-confidence state when warming up; `npm run test` (lint + build) + `npm run smoke` green.

## Verification

TDD throughout; `make backend-test` green at every step (baseline to confirm first: handoff cites **1163 passed, 2 skipped**). Unit tests for: the pure EWMA compute (hand-computed fixture per AC4, seeding, decay, ramp, condition bands, warming-up floor); the daily-series construction (same-day summing, rest-day zero-fill, window bound); `build_readiness` DB read + guard; `_build_training_load_context` pack-section shape (present under v6, absent otherwise, facts untouched, as-of date); `build_system_prompt` v6 composition in **both** opener and fuller modes (predecessors byte-stable, rule 27 present under v6); the `ActivityDetailRead.training_load` projection. The **cross-condition invariance test (AC3)** is the load-bearing gate. `make eval-selftest` green — **no new rubric assertion** (the deterministic harness cannot measure readiness-framing quality; that is the deferred #164 semantic judge): instead confirm the existing ten assertions, including the `voice_preserved_safety_surface` / `corpus_preserved_safety_surface` floor sensors, still pass under `coach_message_v6`. Frontend: `npm run test` + `npm run smoke`. **Real-data**: `make seed-local` → compute readiness over the 454-activity seed; sanity-check the fitness/form trend against Strava Fitness/Freshness (validation-only, divergence = a signal to fix our model). **Pre-flip slow-path verification** (the P1.1 activation lesson, load-bearing because P3 activates in prod): set `COACH_PROMPT_ID=coach_message_v6` locally → generate the two-stage opener→fuller, confirming cache regen, display-safe read, and that the coach visibly contextualizes the run within the training arc — a single ~$0.20 paid LLM run, owner-flagged, run only with explicit go. `aiw-security-testing` is **out of scope** — readiness is derived from existing data, no untrusted input. Coaching-tone/UX quality and the readiness card are owner judgement, surfaced not asserted.

## Out of scope

- **#166** (resting HR / HR recovery capture) and any physiological-readiness layer — readiness is load-derived only; #166 is the clean additive follow-on (it also completes the M9 referral red-flag set).
- **Platform-number cold-start seeding** — platform numbers are validation-only; thin history yields the warming-up abstention, never a borrowed/unit-mapped number.
- **Persisting the model**, a historical PMC-style chart, or a dedicated `/readiness` page — read-time compute is authoritative; persisted-series storage is a separate additive decision if a richer chart is ever wanted.
- **An ACWR injury-risk flag** — derivable from fitness/fatigue on demand later; not a second model in P3.
- **A new validator rule** — readiness is a legitimate tier-3 deterministic fact the coach may cite (like `calibration`/baseline, unlike the voice-only `narrative` and judgment-only `corpus`, which earned not-evidence rules); the existing medical-scope rule (rule 5) and the new prompt rule 27 guard the floor, and the derived dials open no new evidence-laundering path.
- **Feeding readiness into `Salience` / the two-stage trigger** — a possible follow-on; P3 keeps readiness a read-only pack signal with no write-back (the deterministic write-back LLM-free invariant is untouched).
- The #273 regen-race fix, the #274 A3 truncation bug, and the deprecated `Activity.opener_notification_sent_at`/`coach_notification_sent_at` column delete (each a separate tracked task).
