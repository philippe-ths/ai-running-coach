# A4 Cadence + Pipeline Build Brief

> The what. The why and the decision live in `docs/adr/0010-coach-speaks-in-a-two-stage-salience-gated-exchange.md`; the vision in `docs/vision/coach-north-star.md` (decision 3, roadmap A4). New vocabulary (`Salience`) is in `CONTEXT.md`. Owner forks ratified in the 2026-06-11 grill-with-docs session: block-of-one (defer A1); ride `coach_reports` (defer the Exchange table to A1); one prompt two modes; idempotency over timer-cancellation; clean A4 with I1 next (defer all tappable delivery).

## Goal

A finished activity produces a two-stage `Exchange`: a lightweight LLM opener immediately (a brief human reaction plus RPE/pain prompts, never blocking), then a conditional fuller turn (the deep prose coaching) on the runner's reply or a ~3h timer, whichever comes first. Whether stage two fires and how deep each stage goes is gated by `Salience`, computed as a hybrid (deterministic facts plus a new novelty signal, a deterministic safety override, and the opener LLM's depth/schedule judgment). The exchange is one evolving `coach_reports` row produced by one prompt in two modes (`coach_message_v2`, schema 2.0 extended to hold the opener prose); cutover/rollback stays a `COACH_PROMPT_ID` flip. The M4-M10 write-back, `Consolidation`, and the M5 eval gate attach to the fuller turn only.

## Deliverables

1. **Salience substrate** (`app/services/analysis/` + `app/services/coach/context.py`): a deterministic **novelty** signal (first-of-its-kind in the runner's activity history) and a deterministic **safety override** derived from the existing red-flag flags (`illness_or_extreme_fatigue`, sustained pain). Both assembled into the opener's working context. No monolithic salience score; the existing baseline/flag/adherence signals already feed the pack.
2. **Two-mode prompt** `coach_message_v2` (`prompts.py`): supersedes v1, invoked in two modes. Opener mode: lean, a brief reaction, emits RPE/pain tappable prompts, and declares a **schedule-fuller-turn?** judgment (overridden to true by the safety override). Fuller mode: the full discipline of `coach_message_v1`'s rules plus a continuity rule (read the opener, advance not restate, fold in any reply). `coach_message_v1` and `coach_report_v1`..`v10` byte-stable.
3. **Schema extension** (`app/schemas/coach.py`): `CoachMessageReport` gains an `opener_message` (prose) field and a `schedule_fuller_turn` bit; the existing `message`/tail hold the fuller turn. Schema stays 2.0 (coach_message family). The opener's RPE/pain options reuse the existing `questions`/`TappableOption` tail.
4. **LLM call modes** (`llm.py`): an opener call (lean context, short `max_tokens`, mode flag) and the fuller call (full context, continuity inputs), reusing the A3 `generate_coach_message` infra and its strict-parameter surface. Opener output is policed by `validate_message_policy` exactly as the fuller turn is.
5. **Pipeline split** (`app/jobs/`): refactor `process_new_activity` into an **opener job** (ingest -> analyze -> opener generate+store -> notify opener -> if scheduled, `enqueue_in(EXCHANGE_STAGE2_DELAY_SECONDS, fuller_turn_job)`) and a new **`fuller_turn_job`** (idempotency guard on the fuller sentinel -> generate fuller reading opener + replies + full context -> update the row -> notify fuller -> set sentinel -> fire write-back + Consolidation + enqueue eval-eligible). New settings `EXCHANGE_STAGE2_DELAY_SECONDS` (~10800) and `EXCHANGE_REPLY_WINDOW_SECONDS`.
6. **Reply path** (`app/api/`): on `CheckIn` creation and `CoachChatMessage` creation, if the activity's exchange is open (opener sent, fuller not done, opener within `EXCHANGE_REPLY_WINDOW_SECONDS`), enqueue `fuller_turn_job`. Idempotent against a racing timer.
7. **Storage/service** (`service.py`): the opener writes the row in a light state (`opener_message`, no/empty tail); the fuller turn updates the same row in place, preserving the opener prose. Cache identity `(activity_id, prompt_id, schema_version)` unchanged. Write-back and the `consolidate_narrative_job` enqueue move to fuller-turn completion (non-fallback only); the opener writes nothing to durable memory.
8. **Notifications** (`app/services/notifications/`): opener and fuller each send their own `Notification` (the opener brief, the fuller full), both via `_prose.py` rendering. Per-stage dedup: add `Activity.opener_notification_sent_at`, keep `coach_notification_sent_at` as the fuller sentinel. Telegram opener renders prose plus a "let me know how it felt" line and the app link (inline-keyboard buttons are I1).
9. **Frontend** (`frontend/`): the activity page renders the opener prose immediately, then the fuller prose once stage two lands, preserving both as a two-line thread (the seed of the I3 conversation view). `CoachReportPanel` extended; existing A3 chips render but stay non-interactive until I1.
10. **Migration + eval + docs**: alembic migration (opener-prose storage + `opener_notification_sent_at`); the M5 harness scores the fuller-turn message (opener-only rows are not-yet-complete, not scored) and gains cadence-behaviour coverage; ADR 0010 (done), `project-context.md` (pipeline/jobs/prompt-v2/schema-2.0-opener/two-notification/salience), `CONTEXT.md` reconciliation (Salience done; Notification / Notified at updated for two stages).

## Acceptance criteria

- AC1: A fresh activity stores an opener-state `coach_reports` row and sends the opener notification immediately, with no RPE/pain required; an unremarkable run ends there (no fuller turn scheduled, learning loop untouched).
- AC2: A salient run schedules a fuller turn; with no reply it fires on the timer; a `CheckIn` or `CoachChatMessage` within the reply window fires it early; the racing timer then no-ops (idempotent). The fuller turn reads the opener and any reply and advances rather than restating.
- AC3: A red-flag flag (`illness_or_extreme_fatigue`) forces a non-silent opener and a scheduled fuller turn regardless of the LLM's judgment (deterministic safety override), and the policy validator polices the opener prose + tail.
- AC4: A check-in on an activity whose exchange is closed (fuller already fired) or older than the reply window does **not** spin up a new exchange.
- AC5: Two notifications at most per activity (one opener, one fuller), each at-most-once via its own sentinel; regenerating a report (`force=true`) re-fires neither.
- AC6: The fuller turn is a schema-2.0 `CoachMessageReport`; `make eval` scores it with the existing extractors and stays green (no assertion regression vs the live `coach_message_v1` baseline); write-back, `fetch_prior_commitments`, and `consolidate_narrative_job` fire on fuller-turn completion only; `tests/test_writeback_is_llm_free.py` passes unmodified.
- AC7: Frontend shows the opener immediately and the fuller turn once it lands, both preserved (lint + build + smoke green); Telegram sends opener prose then fuller prose as two messages.
- AC8: Rollback rehearsed: flipping `COACH_PROMPT_ID` back to `coach_message_v1` (or `coach_report_v10`) serves the prior single-shot path with zero code change; cached rows render unchanged.

## Verification

TDD throughout; `make backend-test` green at every step. Behaviour-heavy, so weighted to the pipeline/cadence: unit tests for the salience substrate (novelty, safety override) and the reply-window bound; job tests for the opener/fuller split, idempotency, and the timer/reply preemption (fake clock, in-memory queue); a stub-LLM-client path for the two-mode call; eval-selftest for the unchanged fuller-turn scoring. A live cutover rehearsal on `make seed-local` data under `COACH_PROMPT_ID=coach_message_v2` (opener + fuller generation, dedup, the eval compare) is the A4 done-decision evidence and needs owner-authorised paid calls. Production flip is an owner-executed Railway config change.
