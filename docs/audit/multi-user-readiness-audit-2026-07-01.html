Multi-User Readiness Audit

AI Running Coach · Scenario: 10 new people sign in tomorrow and use every feature concurrently · 2026-07-01 · read-only code audit across 5 feature branches

Would it cope?

Not cleanly on day one, but it would not lose or leak data. The multi-tenant foundations are genuinely solid: per-user data isolation is thorough, Clerk auth is sound, Strava webhook routing is correct, and both the global Strava rate budget (#544) and the LLM cost cap are merged and armed in prod. Nobody's run data reaches the wrong person under the live Telegram config.

What breaks the "cope" is throughput and onboarding friction, not correctness: one background worker serializes every coach report (~40–50 min tail for 10 simultaneous reports), the first-sync path can time out under the shared Strava budget, a handful of first-load races throw 500s, and — the one that will actually break features tomorrow — production deploys don't auto-apply DB migrations, so any schema a release expects can simply be absent until an operator runs it by hand.

Critical

Breaks a feature, stalls the system, or is a latent data leak — fix before inviting 10 users.

C1Prod deploys do not auto-apply Alembic migrations

Evidence  Issue #586; docs/deployment/deploy-checklist.md:106 — alembic upgrade head is only a recommended manual pre-deploy step; the v13 cutover required a hand-run migration.
Impact  Any table/column a merged release expects (e.g. runner_memory, exchange sentinels) is missing in prod, so the pipeline 500s on every new user's first activity until an operator manually migrates against DATABASE_PUBLIC_URL.
Fix  Wire alembic upgrade head into both services' Railway Pre-Deploy Command so schema applies atomically with every deploy.

InfraDeploy
C2Single RQ worker processes one job at a time — coach reports back up to ~40–50 min

Evidence  app/worker.py:41 constructs exactly one Worker over one queue, no fork pool; a full report runs ~120–360s (RQ_JOB_TIMEOUT_SECONDS=600).
Impact  10 users' reports on one lane = 10 × ~240s ≈ ~40 min tail for the last runner — before ingest/analyze/self-heal/distill jobs share the same lane, and before the +30 min block-complete debounce herd all fires into it at once.
Fix  Run 2–3 worker replicas (exactly one with with_scheduler) or a dedicated queue for heavy fuller/memory jobs.

InfraCoach/LLM
C3Email channel routes every user's coach report to one global inbox (latent leak)

Evidence  app/services/notifications/__init__.py:60,96 — _resolve_to always returns the global NOTIFY_TO for the email channel, never user.email.
Impact  Inert today (prod runs the Telegram channel), but if a deploy ever has SMTP configured and Telegram not, all 10 users' reports land in one inbox — a direct cross-user privacy leak with nothing enforcing the channel choice.
Fix  Suppress email for non-owner users the same way Telegram does, or hard-gate the email channel to single-user deployments until per-user email (ADR 0023) ships.

Needs improvement

Works but degrades, is fragile, or throws avoidable errors at 10 users.

N1First-sync fetches streams synchronously in-request, ungated by the Strava budget

Evidence  app/api/activities.py:162 → ingestion.py:270 per-activity streams loop inside the HTTP request.
Impact  A new user's 30-day sync fires one streams call per activity in-request; 10 concurrent first-syncs blow the shared 100/15min ceiling and each request blocks past the gateway timeout — onboarding sync appears to hang/fail.
Fix  Move the default-window sync to a background RQ job returning 202 that yields to over_budget() between activities.

StravaOnboarding
N2Strava token refresh has a check-then-refresh race that can brick an account

Evidence  ingestion.py:98 ensure_valid_access_token — unlocked read of expires_at, then refresh + commit.
Impact  During onboarding a user's webhook, self-heal, and backfill run together; two can both refresh, and Strava rotates (invalidates) the refresh token, so the second uses a stale token and can permanently unlink that account.
Fix  Serialize refresh per account with a short Redis lock or SELECT ... FOR UPDATE on the StravaAccount row.

StravaData integrity
N3Singleton get-or-create (UserProfile / CoachingRelationship) is not race-safe on first load

Evidence  app/api/profile.py:42 — bare select → add → commit with no IntegrityError recovery (the User insert already does this; the profile path was missed).
Impact  A new user's first screen fires /profile, /coach/voice, /coach/stance concurrently; all three miss the SELECT and INSERT, the losers hit the unique constraint and 500. Self-heals on retry, but every new user sees errors on their first screen.
Fix  Reuse the same rollback-and-re-select IntegrityError recovery already used for User.

AuthOnboarding
N4Expired/absent Strava OAuth state strands a real user on an orphan placeholder account

Evidence  app/api/auth.py:123 — on unresolvable state, links to the sole user only if len(existing_users)==1, else mints strava-{id}@placeholder.invalid; state TTL 600s (oauth_state.py:29).
Impact  With >1 user, a runner who lingers on Strava's consent screen (state expires) gets a new orphan placeholder user; their real account has no Strava link but the app reads "connected". No misroute, but the connect is silently lost.
Fix  In production, reject an absent/invalid state on the new-athlete path (prompt reconnect) instead of the placeholder fallback; consider a longer TTL.

StravaAuth
N5Notification cross-tenant safety hinges on unguarded OWNER_EMAIL config

Evidence  app/services/notifications/__init__.py:94 — the #542 leak-close only engages when OWNER_EMAIL is non-empty; unset/typo'd reverts to single-user mode.
Impact  If OWNER_EMAIL is ever unset on a multi-user deploy, all 9 non-owner runners' coach reports route to the owner's global Telegram chat. Set in prod today, so this is config fragility, not a live leak.
Fix  Fail closed (return None) for an unbound non-owner whenever more than one user exists, and add a production boot guard.

NotificationsConfig safety
N6Strava budget gate is checked once per batch, not per call — concurrent backfills overshoot

Evidence  backfill_streams.py:163 — single over_budget() at batch start, then up to 20 uninterrupted streams calls.
Impact  10 per-user backfill chains all pass the gate in the same window, then each fire ~20 calls ≈ 200 requests before any re-check, overshooting Strava's 100/15min despite the gate; the tiny 429 backoff becomes the real floor.
Fix  Re-check over_budget() inside the per-activity loop before each streams call.

Strava
N7Strava 429 handling gives up after 2 retries and caps Retry-After at 60s

Evidence  http_adapter.py:19 _MAX_RETRIES=2, :22 _MAX_RETRY_AFTER_S=60 — below Strava's up-to-15-min window.
Impact  When the shared short window is exhausted, live calls (sync list_recent_activities) raise and fail the whole operation rather than recovering — users see hard errors during contention.
Fix  On the live path surface a "rate-limited, retry shortly" state or honor a longer Retry-After; let the budget gate absorb the wait on background jobs.

Strava
N8Anthropic 429 is never retried — silently degrades to a fallback report

Evidence  app/services/coach/llm.py:117,231,310 — retry only on status_code ≥ 500; no RateLimitError/429 handling anywhere in the coach layer.
Impact  Concurrent worker fuller turns + web chat streams can trip Anthropic's per-minute limit; a 429 (<500) is raised immediately and the report is stored is_fallback=True — the runner silently gets a template instead of a real report.
Fix  Catch anthropic.RateLimitError and retry with exponential backoff honoring Retry-After before falling back.

Coach/LLM
N9New unbound runners get zero push delivery, silently

Evidence  notifications/__init__.py:100 returns None (suppressed) for an unbound non-owner; process_new_activity.py:124,265 pass it through.
Impact  A user who connects Strava but hasn't done /start Telegram linking gets no receipt, opener, or report on any channel (email is owner-only too). Nine of ten new users see nothing pushed until they link, with no in-band nudge.
Fix  When a recipient resolves to None, surface an in-app "link Telegram to get coached" prompt so the drop is visible.

NotificationsOnboarding
N10Postgres connection pool is unmanaged (default 5 + 10 overflow per process)

Evidence  app/db/session.py:11 — create_engine sets only pool_pre_ping; no pool_size/max_overflow/pool_recycle.
Impact  Web and worker each open their own 15-connection pool against one Railway Postgres; concurrent bursts plus background jobs approach the plan's connection ceiling, and a leaked session blocks the pool for 30s before erroring. Thin, unmanaged headroom at 10 users.
Fix  Set explicit pool sizing tuned to Railway's Postgres limit and the process count.

Infra
N11Web service likely runs a single uvicorn worker

Evidence  No gunicorn dependency; Railway start command uvicorn app.main:app with no --workers (topology.md:46) → one process.
Impact  One worker serves all /api/* traffic for 10 people plus inbound webhooks; a single slow synchronous handler head-of-line-blocks everyone. Async reads are fine, but there is zero horizontal headroom.
Fix  Run uvicorn with --workers N (or gunicorn+uvicorn workers) sized to CPU.

Infra
N12Aux Haiku jobs (distill / memory / receipt-voice) are record-only, no entry gate

Evidence  material_distiller.py:176, memory_update.py:472, receipt_voice.py:250 call budget_record but never budget_over before the call.
Impact  When the cap trips, the main report + chat degrade correctly, but every upload/memory-rebuild/voice-regen still fires a Haiku call and only accounts for it afterward, so aux spend overshoots the ceiling. (Deliberate — background jobs must not hard-fail on budget.)
Fix  Add a soft over-budget skip on the non-essential ones (receipt-voice regen, memory-update) so they pause instead of overshooting.

Coach/LLMCost
N13Telegram global-owner-chat inbound path bypasses the per-activity ownership check

Evidence  app/api/webhooks.py:447,473 — a tap from the global TELEGRAM_CHAT_ID is treated as bound_user=None, so the activity.user_id != bound_user.id guard is skipped.
Impact  That chat (the deployment owner's) can write a CheckIn / "done" to any user's activity. Exposure is limited to the single owner chat, but the authorization hole is real.
Fix  Resolve the global-owner chat to its actual User and run the same ownership check; drop the unauthenticated path once the owner binds their own chat.

Auth

Foundations that are already sound

  • Per-user data isolation — every application router scopes reads/writes by user.id; shared helpers (get_owned_activity, chat's _build_cross_activity_block) require a user_id filter; cross-tenant ids return 404, not a leak.
  • Clerk auth — RS256-pinned JWT verification, issuer/azp checks, resolution by verified email, race-safe User creation, production fail-closed 503 when unconfigured (#480).
  • Strava webhook routing — create/update/delete resolve the owner via StravaAccount.strava_athlete_id; the #512 object-owner bind stops athlete B acting on athlete A's activity. No single-owner fallback on this path.
  • Telegram /start binding — single-use Redis nonce (GETDEL, 10-min TTL), per-user tokens, stale-claim clearing before rebind; 10 concurrent linkers cannot cross-bind or replay.
  • Global Strava rate budget (#544) — MERGED and armed in prod (75/15min, 800/day backstop); metered calls record to a Redis counter, background jobs defer on over_budget(). Prevents total collapse.
  • LLM cost cap — a HARD entry gate on the two paths that dominate spend (report + chat); prod auto-applies a global backstop, armed at $10 global / $5 user windows.
