# Training load is a read-time EWMA fitness/fatigue/form model the coach reads through a gated pack section under a new prompt id

The north-star (`coach-north-star.md` §1 brain-dump, §3 Decision 9) asked for our own deterministic read of the runner's *current condition* — "so our AI can more accurately determine the user's current condition" — reproducing what Strava (Fitness/Relative Effort) and Garmin (Training Load) surface, but device-independent and auditable. #186 shipped the prerequisite: a per-activity `effort_score` that is one comparable, summable unit across HR / no-HR / non-run activities (Edwards "zone-minutes"). P3 builds the multi-day model on top of that primitive. This ADR decides the model's math, where it is computed, how it reaches the coach, and where the milestone draws its boundary — mirroring how the corpus (ADR 0014) and stance (ADR 0015) were handled.

**The decision.** `Training load` is a **read-time EWMA fitness/fatigue/form model**, computed from the per-activity `effort_score`, surfaced to the coach through a **new gated `training_load` context-pack section under a new prompt id `coach_message_v6` (= `coach_message_v5` + a static readiness addendum, prompt rule 27)**, with platform numbers kept strictly validation-only.

1. **The model is EWMA fitness/fatigue/form (the Banister / TrainingPeaks Performance Management Chart), not flat rolling sums or an acute:chronic ratio.** Daily `effort_score` feeds two exponentially-weighted moving averages: **fitness** (chronic load, ~42-day time constant), **fatigue** (acute load, ~7-day time constant), and **form** (their balance, fitness − fatigue), plus a **ramp rate** (how fast fitness is rising). This is exactly what Strava Fitness/Freshness and Garmin Training Load implement, so it directly answers the "reproduce the platform read of current condition" ask and validates against their numbers. EWMA is robust to this runner's gappy, mostly-summary-imported (Tier-B) history — no week-boundary artifacts, and rest/missing days decay naturally. The acute:chronic ratio (Gabbett ACWR) is derivable from fitness/fatigue on demand if an injury-risk nudge is wanted later; it needs no separate model.

2. **It is computed at read time, mirroring the M9 calibration pattern — not persisted in a table or on `RunnerBaseline`.** A pure function recomputes the EWMA over a bounded window of the runner's recent daily load (~182 days, reusing the M2 baseline window length), EWMA-seeded at the window start so older history is forgotten and per-read cost stays flat as history grows (the #167 concern). Read-time computation is required, not merely convenient: the just-analyzed run must be in the acute load for today's report, and `RunnerBaseline` is recomputed *after* the analysis pipeline — the exact reason M9 calibration computes at read time rather than reading the after-analyze baseline. This avoids a migration and any staleness/consistency burden on add/edit/soft-delete/out-of-order sync (the burden the #209 weekly view also avoids by computing at read time).

3. **The coach reads it through a new `training_load` pack section gated to a new prompt id.** Because `coach_message_v5` is live in production and the standing discipline is that predecessor prompts stay byte-stable, a section the coach reads cannot be retrofitted onto v5 (that would silently change live behaviour and regenerate every v5 report). A new prompt id is therefore unavoidable the moment the coach reads a new section. Given that cost is already paid, `coach_message_v6` carries an explicit **prompt rule 27** (the `Vn = V(n-1) + addendum` idiom): use the readiness read to contextualize today's run within the training arc; it never overrides this run's re-derived `DerivedMetric`, never reads a negative form / high ramp as an overtraining or medical verdict (the safety floor, the #168 load≠intensity lesson one layer up), and is ignored while the model reports itself warming up. A new `TRAINING_LOAD_PROMPT_IDS = {coach_message_v6}` gates both the section and the addendum; the pack stays byte-stable for every other prompt (the `corpus`/`stance`/`block` Optional-and-drop idiom).

4. **Platform numbers are validation-only — never authoritative, and never even a cold-start seed.** Strava/Garmin load numbers are a different unit on a different scale from our Edwards zone-minutes, so seeding our chronic baseline from them would require an unvalidatable unit mapping. Instead, when a runner's history is shorter than the chronic window the model labels itself **warming up** (low confidence) and rule 27 makes the coach abstain from a confident condition verdict rather than guess. Platform numbers stay a manual cross-check that our fitness/form *trend shape* tracks theirs; a divergence is a signal to fix our model, not to defer to it. This strengthens the north-star's "platform never the source of truth" rule to "platform never even a seed."

5. **Resting HR / HR recovery (#166) is out of scope.** P3 readiness is load-derived only — fully computable from `effort_score` today. A physiological-readiness layer (resting HR, HRR) needs a data source the app does not capture (`calibration.py` records this gap explicitly) and is a clean additive follow-on that also completes the M9 referral red-flag set; gating the shippable load model behind a new ingestion pipeline would be the wrong trade.

## Considered options

- **Flat rolling sums + acute:chronic ratio (Gabbett ACWR).** Rejected: simpler and reuses the #209 weekly view's shape, but it is coarser (sensitive to window boundaries), framed as injury-risk rather than "current condition / fitness / form," and diverges from the Strava/Garmin fitness/freshness mental model the owner cited as the origin. EWMA reproduces the platforms directly and can still derive the ratio.
- **A "both" model — EWMA for condition plus a standalone ACWR injury flag.** Rejected: two models to validate and maintain and more pack surface, when the ratio is derivable from the EWMA fitness/fatigue values on demand. Earns little over deriving it when needed.
- **Persist the model in a new table (daily snapshots or a current-condition row) or on `RunnerBaseline`.** Rejected: a table adds a migration and a recompute-on-every-mutation consistency burden; `RunnerBaseline` is recomputed *after* analyze, so a readiness read off it would exclude today's run — semantically wrong for a "current condition" signal and the precise reason M9 went read-time. Read-time computation is correct here, not just cheaper.
- **Surface readiness under the live `coach_message_v5` (no new prompt id).** Rejected: impossible without breaking the byte-stability discipline — adding any section the coach reads changes the v5 pack and silently regenerates live reports. A new section the coach reads forces a new prompt id; there is nothing cheaper to gain by avoiding it.
- **Cold-start the chronic baseline from a platform number for a thin-history runner.** Rejected: a unit mismatch (their numbers are not Edwards zone-minutes) we cannot validate, and untested dead code for this full-history single runner. The warming-up abstention is the honest behaviour and keeps the platform-never-authoritative rule clean.
- **Pull #166 (resting HR / HR recovery) into P3.** Rejected: no data source exists today; it would expand P3 well beyond the device-independent load model the north-star asked for and delay it behind a new capture pipeline. It is a clean additive milestone.

## Consequences

- P3 ships: a pure `services/readiness.py` EWMA fitness/fatigue/form model (windowed, seeded, read-time); a `_build_training_load_context` in `context.py` emitting a `training_load` pack section gated to `coach_message_v6`; `coach_message_v6` (= v5 + rule 27) with a `TRAINING_LOAD_PROMPT_IDS` gate (predecessors byte-stable); a read API endpoint; a readiness card on the activity detail page; and a documented set of owner-tunable constants (the two time constants, the condition-label bands, the ramp-rate threshold, the warming-up sample/window floor).
- Because v6 carries a new `training_load` section, v6 reports legitimately regenerate (the M0 versioned-cache idiom); pre-readiness history is retained.
- Activating v6 in prod jumps `coach_message_v5 → v6`, turning on the readiness surface on top of the already-live voice/corpus/stance. The repo config default stays `coach_report_v10`. The flip is an owner-authorized, owner-executed Railway `COACH_PROMPT_ID` change; the slow/worst-case generation path is verified before the flip (the P1.1 activation lesson) and confirmed live after, and the #273 delete-then-generate regen race is respected (no regenerate until the worker redeploy is fully complete).
- Readiness is a new tier-3 deterministic durable fact in `Authority tiering`: it grounds readiness judgment but never overrides this run's measured data or the safety floor — enforced in three layers exactly as the corpus/stance are (prompt rule 27, the existing narrow validator rules, which fire regardless of what steered the output, and the eval safety-surface assertions, which must continue to hold under v6).
- If #166 later adds a physiological-readiness signal (resting HR / HRR), this ADR is *augmented* (readiness fuses a second input), not reopened. If the model's outputs are ever persisted for a richer historical chart, that is a separate, additive storage decision that does not change the read-time-is-authoritative contract.
