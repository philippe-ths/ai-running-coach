## Product Summary

Running Coach is a multi-user app that connects to Strava, ingests running activities, computes training signals, and produces opinionated post-run analysis.
Each runner signs in with social login (Clerk, ADR 0022; the verified email is the durable identity) and connects their own Strava account; the app runs either locally via docker compose or as a deployed multi-user instance on Railway (backend, Postgres, Redis) and Vercel (frontend). Multi-user signup shipped in Phase 2 (ADR 0022 identity + ADR 0006 self-heal sync, merged 2026-06-24); per-user Strava linking and Telegram routing are the remaining follow-ups (#477), so those surfaces stay single-user until they land.
The core flow is: connect Strava → sync activities → deep-process a run → view derived metrics and an LLM-generated coach report on the activity page.

## Domain Concepts

A `User` owns a `UserProfile` (goal, experience, weekly volume, max HR, races, injuries, plus the runner's Strava-sourced HR-zone lower bounds `hr_zones`/`hr_zones_source` used to bin time-in-zone, #297, and the runner's chosen `week_starts_on` — Monday (0) or Sunday (6), null resolving to Monday — that sets the week boundary across the coach pack and Trends, #676, plus the runner's stated build `weight_kg`/`height_cm` — nullable floats meaning NOT STATED rather than average, envelope-validated at the API so a unit slip never reaches the coach as a fact, #742) and a linked `StravaAccount` (OAuth tokens, athlete id); `User.telegram_chat_id` (nullable, P2.4/#120/ADR 0023) is the user's bound Telegram chat for per-user notification routing (null = fall back to the configured global recipient).
An `Activity` is a single Strava activity record owned by a `User`, identified by `strava_activity_id`.
An `ActivityStream` holds per-sample time-series data (HR, pace, cadence, power) attached to an `Activity`.
A `DerivedMetric` row attaches one set of computed signals to one `Activity` (activity class, effort score, pace variability, HR drift, time-in-zones, stops, efficiency, intervals, flags, confidence, risk, discount signals, consolidated stream view). The consolidated stream view (A2a) is a small downsampled aligned HR/pace/grade/cadence snapshot, a processed artifact derived during analysis and pulled on demand, never a source of truth.
`effort_score` is the per-activity training-load primitive (#186): Edwards-style zone-minutes (`Σ minutes-in-zone × zone-number`, with moving time below Z1 or in HR gaps counted at weight 1), estimated per data tier — a real HR-zone distribution, else the zone of the summary `avg_hr` against the athlete max, else session-`CheckIn.rpe`, else a default aerobic weight (zone 2) — so it is one scale comparable and summable across activities with and without HR (the primitive the P3 acute/chronic `Training load` readiness model sums, #276/ADR 0016); the migration `5f60bc938518` recomputed it across all historical `DerivedMetric` rows.
A `Block` (A1, ADR 0011) groups a user's temporally-contiguous activities into one training event by deterministic time-gap clustering (an activity strictly under `BLOCK_GAP_SECONDS` from an existing block joins it, symmetric so out-of-order sync converges; a block whose exchange is closed never absorbs — the late activity starts a new block), carrying `start_date`/`end_date`, a `primary_activity_id` (the run, else the longest member; frozen once the block's exchange has opened so the report anchor never moves; recomputed by explicit corrections), and a `user_corrected` audit bit; `activities.block_id` is the membership FK, assignment runs at ingestion on every ingest path, and the A1 migration backfilled every analysed non-deleted historical activity into a block-of-one.
An `Exchange` (A1) is the first-class two-stage lifecycle row for one `Block` (`block_id` UNIQUE, created with the block): `opened_at` marks opener generation (anchors the reply window, independent of delivery so a NoOp local notifier still works), `opener_sent_at`/`fuller_sent_at` are the per-stage at-most-once notification sentinels relocated from `Activity` (whose `opener_notification_sent_at`/`coach_notification_sent_at` stop being written under the two-stage path but are retained — their removal is a separate approved delete; the single-shot rollback path still dedups on the Activity sentinel because per-activity dedup needs a per-activity store), and `fuller_sent_at` set means the exchange is CLOSED; backfilled exchanges read as closed. `coach_reports` is untouched: still the versioned generation artifact keyed `(activity_id, prompt_id, schema_version)` on the block's primary activity. Under the #296 receipt cadence (ADR 0018, gated by the orthogonal `COACH_RECEIPT_CADENCE` flag) the same row carries a shifted meaning: `opened_at` = the first instant deterministic receipt for the block (there is no LLM opener, so `opener_sent_at` is unused), the new `done_at` records the runner's explicit "done" tap, and `fuller_sent_at` stays the CLOSED sentinel — now the full report, fired ~`BLOCK_GAP_SECONDS` after the session goes quiet (the block-complete debounce) or on a "done" tap, with the 3h `EXCHANGE_STAGE2_DELAY_SECONDS` timer retired; per-activity receipt dedup lives on the new `Activity.receipt_sent_at`.
A `CoachingRelationship` (A1) is the thin one-row-per-user durable anchor of the coaching relationship (id, unique `user_id`, `created_at`), auto-created on first profile read like `UserProfile`. P1.1 (ADR 0012/0013) extends this row with the runner-declared coach Voice: `voice_preset`, the five 1-5 dials `voice_warmth`/`voice_humor`/`voice_force`/`voice_energy`/`voice_length`, and the `voice_freetext` escape-hatch (all nullable; null resolves to the balanced 3/3/3/3/3 default at read time). #822 reshaped the axis set from four tonal dials to five orthogonal ones — Warmth (Hostile↔Devoted), Humor (Deadly serious↔Comedic), Force (Gentle↔Brutal, IMPACT rather than the old Directness's clarity), Energy (Flat↔Explosive) and the new Length (Terse↔Expansive, which nothing previously controlled and which moves the read more than any tonal axis) — via migration `a1c4e77b9d02`, a RENAME of `voice_directness`→`voice_force` plus an added `voice_length`, so declared voices carry through unchanged. A runner who selects a character and nudges a dial is on that character ADJUSTED: the base and its deltas are derived from the stored preset key and dial values (`voice.dial_deltas`/`is_customised`), never recorded separately, so a dial cannot drift out of sync with the base it came from. Voice is runner-sovereign: the runner declares it and the only writer is `PUT /api/coach/voice`; no background job ever infers or mutates it (no secret adaptation). Voice flexes delivery only and never the facts, grounding data, or safety floor (ADR 0013) — since #822 that is STRUCTURAL rather than instructed, because voice no longer reaches report generation at all (see the voice rewrite pass below) — and remains enforced by the voice-agnostic context pack + policy validator, a deterministic cross-voice invariance test, and a soft `voice_preserved_safety_surface` eval assertion. P1.3 (ADR 0015) further extends this row with the runner-declared coach Stance: `stance_school` (a `corpus.SCHOOLS` key the coach reasons from) and the two 1-5 emphasis dials `stance_data_sentiment` (Data↔Sentiment) and `stance_process_outcome` (Process↔Outcome) (all nullable; null resolves to the default school aerobic-base + balanced 3/3 at read time, a zero-backfill migration). Stance is runner-sovereign like Voice (the only writer is `PUT /api/coach/stance`; no background job infers it) and goal-tethered: it reweights emphasis/method-framing only, never the facts or the safety floor, enforced by the cross-stance invariance test and the `corpus_preserved_safety_surface` eval assertion (which holds across schools). Stance carries NO free-text — runner-supplied coaching philosophy is `User materials` (P4), not stance. The #296 receipt cadence (ADR 0018) further extends this row with the pre-generated voiced receipt templates: `receipt_templates` (a `{situation: [variants]}` JSON map produced OFFLINE through the runner's Voice, null = the house-default floor), `receipt_templates_voice_key` (a fingerprint of the voice inputs the set was generated from, so a voice change is detectable), and `receipt_templates_generated_at` (provenance); the only writers are the offline `generate_receipt_templates_job` (enqueued on `PUT /api/coach/voice` and lazily when a receipt finds none) — the deterministic receipt only ever READS them.
A `CheckIn` captures subjective post-run input from the user against an `Activity`.
A `CoachReport` is the cached LLM analysis for an `Activity`, keyed by `(activity_id, prompt_id, schema_version)` so a prompt/schema change retains prior-version reports instead of overwriting them; its `report` JSON holds one of two shapes by schema-version family (ADR 0009): the legacy structured `CoachReportContent` (schema 1.2) or the A3 prose `CoachMessageReport` (schema 2.0, a human prose `message` plus a thin structured tail). Under the A4 two-stage Exchange (ADR 0010) the schema-2.0 `CoachMessageReport` also carries an `opener_message` (the stage-one prose) and a `schedule_fuller_turn` bit; one evolving row holds both stages (the opener writes `opener_message` with `message` empty, the fuller turn fills `message` in place preserving the opener). `CoachChatMessage` rows form the runner's follow-up conversation, stored against a `Thread` (#765, ADR 0027): a `Thread` is the runner-initiated, relationship-scoped conversation unit (one row per conversation: `user_id`, an optional `activity_id` anchor as a framing hint, a nullable runner-visible `title`, `last_message_at` for switcher recency), every conversational turn reads and writes through a thread (resolve-or-create in `services/coach/threads.py`, orphan pre-thread rows adopted on read), an anchored turn dual-writes `activity_id` so the activity-scoped readers (memory sources, adherence pushback, fuller-turn continuity, the activity-scoped history read) are unchanged, and each turn stores per-turn provenance (`asked_from` the screen label, `tools_used`, `skills_used`); the migration `14eca2b25785` backfilled every activity-with-chat into one anchored thread with nothing lost. The thread API (#766) adds the switcher surface under `/api/coach/threads` (list with server-resolved display titles — the written title, else the trimmed first user message — plus snippet and anchor summary; read; rename; hard delete) and the thread turn `POST /api/coach/threads/messages` (SSE; absent `thread_id` creates the thread, optionally anchored to an owned activity, and announces it as the stream's first object frame): the turn assembles a relationship baseline (`services/coach/thread_turn.py` — profile incl. stated build, the runner memory profile, a current readiness read, the declared Voice, and a bounded cross-THREAD digest that replaces the cross-activity digest for thread turns) instead of a stored report pack, shares the buffer-then-validate generation core and medical-scope floor in `chat.py` (`_buffered_tool_loop`/`_validate_conversational_text`), can let the model mint one ephemeral server-stored proposed action from a fixed reversible set — `check_in`, `intent`, `split_block`, `merge_blocks`, and (#830) `complete_session`, ticking a `PlannedSession` done, which the runner can still untick by hand — that streams as a structured frame and only writes when the runner later confirms its single-use token through the confirm endpoint, bounds LLM history to the last 40 turns while scrollback stays complete, and declines over-budget turns with a what-still-works message; after the first exchange an untitled thread gets a written title (one hardcoded `claude-haiku-4-5` call in `app/jobs/thread_maintenance.py`, budget-recorded, never overwriting a runner-written title), and a thread gone quiet for `BLOCK_GAP_SECONDS` fires one `update_memory_job` pass per runner per hour. Screen context (#767, ADR 0028) makes the thread turn screen-aware as a SERVER-RESOLVED POINTER: the client sends `ScreenPointer` (screen key + view selections only — an enum-typed shape with `extra="forbid"`, so a fact can never travel from the client), `services/coach/screen_context.py` resolves it owner-scoped through the same builders that produced the screen (activity → `query_tools.get_session_detail`, trends → `services/trends.get_volume_report`; Load/Home/Activities/Profile/Schedule are identity-only since the baseline already carries their content — #830 added the `schedule` key to `ScreenPointer`'s closed `Literal` and to `screen_context._SCREEN_TITLES` alongside it, both required since `ScreenPointer` forbids extras and an unrecognised screen key 422s the whole turn, and `CoachSheetContext.screenFromPathname` gained the matching `/schedule` → `schedule` mapping; a cross-user or unknown id resolves to nothing), and only the CURRENT screen's view rides the prompt's LOOKING AT section — past turns keep their `asked_from` label, never a second copy of the data. The conversational policy floor is re-sourced from the turn's own facts (`chat._validate_conversational_text`): medical scope unconditional, zone language from the runner's profile calibration (the shared `context.zones_calibration` helper), interval-execution claims gated against the sessions actually fetched or shown this turn (the buffered tool loop banks raw tool results for this); the floor no longer depends on a stored pack parsing at all, so #685's no-report window cannot degrade it. Coaching skills (#769, ADR 0029) give the thread turn house-authored PROCEDURES for hard kinds of request, disclosed progressively: the system prompt carries only each skill's name and one-line "use when" (`coaching_skills.render_catalogue`), and the model pulls the full procedure with the `load_coaching_skill` tool, which rides the SAME tool round as a data fetch and emits no status/trace affordance (it is a procedure, not a lookup) so a skilled turn keeps its lookups — `_MAX_TOOL_ROUNDS` rises 3→4 for the slack. A skill says how to conduct a turn and never what is true about training (any belief belongs in `corpus.py`, so the runner's selected school still governs the substance), can never invent a proposed action or lower the safety floor (the same validator runs over a skilled reply), and is code-resident and house-authored — never runner-supplied, since runner-supplied procedure is `User materials` under ADR 0017's containment. Each skill records WHY it exists in `earned_by` — an observed failure with the request that produced it, or an explicit note that it was authored for coverage — so a later reader can retire one that never earned its keep. The set covers the four request kinds ADR 0029 names: `plan_the_week` (earned by a live turn where a training question carrying a stated symptom had its whole reply withheld by validator rule 5 and replaced with the canned medical redirect, so the runner got a referral and nothing about their training), `compare_sessions` (earned by a probe that returned a multi-part clarifying question, mislabelled a weekday, and fetched neither session's detail), `explain_a_metric` (earned by a probe that graded the runner against a published population band and called a drift figure 'solid' on the run whose own report had flagged it as heat-inflated), and `race_readiness` (authored for coverage; its probe found no defect). The always-on cost is the catalogue only (~830 chars against ~7.9k of procedure held back), pinned by test. The loaded procedures are recorded on the assistant row's `skills_used`. The sheet renders the context ribbon (LOOKING AT · screen · selections — the only thing that animates on navigation) and pages with parameterised state publish selections via `usePublishScreenSelections` (the Trends page publishes range + type filter); a screen change never provokes a turn. #770 retired the activity page's own chat box, the last surface that held a second conversation over one relationship: the page keeps its report, and its conversational question options open the SHEET on that run's thread with the question in the composer (`CoachSheetContext.openWith`, prefilled rather than sent so the send waits for the sheet to resolve which thread it is in). Deleted with it: `CoachChat.tsx`, the `POST /api/activities/{id}/coach-chat` endpoint, `chat.stream_chat_response`, the activity-chat system prompt (`CHAT_SYSTEM_TEMPLATE`/`_build_chat_system_prompt`), the pack-based `_validate_chat_text`, and the read-time cross-ACTIVITY digest `_build_cross_activity_block` that simulated relationship continuity before threading was real (#339's Fork 2 — the real cross-THREAD digest in `thread_turn.py` is Fork 1 landed). The activity-scoped `GET`/`DELETE /api/activities/{id}/coach-chat` remain as owner-scoped API surface. The conversational READ path threads the relationship: it speaks in the runner's declared Voice and carries the report's authority-tiering disciplines (I2, #337, the shared `chat._render_authority_tiering` briefing only the tiers actually in front of the coach). Beyond its frozen baseline it can FETCH training data on demand (#648): a bounded agentic tool loop (`chat._buffered_tool_loop` over `AnthropicClient.stream_chat_turn`, at most `_MAX_TOOL_ROUNDS` rounds with the final round tools-off so it always terminates) lets the coach call three narrow, owner-scoped, coach-framed read tools in `query_tools.py` (`list_activities_in_range`/`get_session_detail`/`get_training_summary`, server-resolved named windows that echo their resolved range, `records_begin`/`coverage_note` so the coach never claims a superlative its partial record cannot support) instead of asking the runner for data the app already stores; owner scoping is server-held from the authenticated runner (a model-supplied id can only narrow within their own data), only the final assembled reply is policy-validated (the #340 floor unchanged), and an ephemeral tool-specific status affordance rides the SSE stream while a tool round runs. The coach-report read endpoint is display-safe (#261): `get_displayable_report_row` serves the active-version row if present, else the most recent cached report of ANY version, so flipping `COACH_PROMPT_ID` (e.g. activating voice `coach_message_v3`) leaves prior-version reports rendering instead of 404-ing or triggering a synchronous on-demand regeneration that exceeds the gateway timeout (the latent #260 bug); the M0 versioned-cache identity used for regeneration (`get_active_report_row`/`get_or_generate_coach_report`) is unchanged, so the background pipeline still generates the active version for new activities and `force=true` still regenerates it.
A `RunnerBaseline` (one row per user) stores rolling baselines used for comparison and drift detection: per-user scalar typicals plus a `bucketed_trends` JSON map of EF and HR-drift trends bucketed by `effort|terrain|temperature-band`, computed by `services/analysis/baseline.py` and recomputed at the end of `analyze` over a rolling `BASELINE_COMPARISON_WINDOW_DAYS` (182d / ~26wk) window anchored on the runner's most recent activity (so per-activity recompute cost stays flat as history grows, #167); a bucket abstains until it has `MIN_SAMPLES_FOR_TREND` (4) like-for-like samples.
A `RunnerMemory` (one row per user, `user_id` UNIQUE, ADR 0025/M1) is the durable runner memory profile that REPLACED the retired belief (`CoachingContext`) + narrative (`CoachNarrative`) loop: a `RunnerMemoryProfile` of five capped, plain-language sections (`who_you_are`/`limits_and_constraints`/`goals_and_plans`/`what_works_for_you`/`lately`) stored as JSON and strict-coerced (`extra="forbid"`, per-section count and per-line length caps), plus provenance (`model_id`/`source_report_count`/`grounded_through`) so a thin/stale profile can be hedged. It holds only STATED facts the runner told the coach plus soft non-gating character, never an inferred behavioral verdict (the rest-day-fixation incident's failure mode), and the writer rebuilds it WHOLE from the raw sources every update pass and never reads its own prior value, so the anti-echo guarantee is a property of input construction. It is the citable `Stated memory` tier: the coach may cite it but it yields to this run's re-derived `DerivedMetric` on a factual conflict and never lowers the safety floor (the v13 memory addendum); there is no "memory-is-not-evidence" validator rule because the tier is grounded by design. Distinct from `RunnerBaseline` (numeric norms) and the deterministic calibration/load signals (re-derived every run, never stored as a verdict).
A `StravaImport` (#239) is the resumable-state row for one historical Strava import: the runner-chosen `since_date` lower bound, a `status` (`running`|`completed`|`failed`), the 1-based `cursor_page` (the next page to fetch, advancing one per full batch so an interruption resumes without re-walking completed pages), an `activities_imported` progress counter the UI polls, and a nullable `error`. All state lives in the row, and dedup by `strava_activity_id` through `upsert_activity` makes any replayed page idempotent.
A `UserMaterial` (P4, #285, ADR 0017) is one runner-uploaded markdown coaching material (their methodology, a coach's plan, a physio protocol, a race plan, a book passage) — the product's first genuinely untrusted-input surface, scoped per `user_id` (many rows per user). It stores the untrusted `raw_text` (source of truth, pull-on-demand, never placed into a prompt and never echoed back over the API) and a `distilled` corpus-`School`-shaped record (`stance`/`principles`/`method_framing`/`emphasis_hints`) produced on ingestion; `status` is the lifecycle (`processing` → `active`|`failed`, `archived` = soft-hide), `content_hash` (sha256 of raw_text) dedups identical re-uploads and drives the failed-retry path, and `distill_model`/`distilled_at` are provenance. Safety is containment, not detection (ADR 0017): the distiller emits structured-output-only and the result is coerced through the strict `DistilledMaterial` schema (`extra` forbidden, fields length/count-bounded), so an off-shape or rogue-key output fails the distillation rather than storing anything off-contract. As of slice 2 (#286) the distilled record is consumed ONLY under a user-materials-aware prompt (`is_user_materials_prompt` — `coach_message_v7` and the live `coach_message_v8`): `retrieval.fetch_corpus(db, user_id, school_id)` reads the runner's `active` materials (newest-first, soft-capped at 10, each coerced through the strict `DistilledMaterial` schema with off-shape rows skipped) into `Corpus.user_materials`, `context._build_corpus_context` carries them as a `user_materials` sub-field INSIDE the `corpus` pack section tier-tagged above the house school (only under `is_user_materials_prompt`, byte-stable under every other prompt), prompt rule 28 and validator rule 8 (`user_materials_cited_as_fact`) bound their authority (reference not instructions; beat house philosophy for stance; never override measured data, the runner's goal, or the safety floor), and the eleventh eval assertion `user_materials_preserved_safety_surface` plus the cross-material invariance test guard the floor; under v6 and below the materials stay inert (the prod `v6→v7` flip is the owner-gated slice #288).
A `GoalRace` (#830) is the runner's own stated race — `name`, `race_date`, `distance_m`, and a `priority` of `A`/`B`/`C` (the runner's own ranking, `A` the race the block is built for, `B`/`C` races run through en route; never a claim about ability) — the typed anchor `UserProfile.upcoming_races` never was: that field is an untyped JSON blob nothing in the backend has ever read (not the coach pack, not the thread turn, not one service), and it is left in place rather than removed (its own dependency sweep, since the frontend profile type and form still round-trip it). A `TrainingPlan` (#830) is the container for what a plan is made of: a nullable `goal_race_id` pointer, a `horizon_end`, and two strict-coerced JSON columns — `rules` (`List[SpacingRule]`) and `week_shapes` (`List[PlannedWeekShape]`, the horizon's per-week load/mix/phase, concrete for ~3 weeks and shape-only beyond) — the `RunnerMemory`/`CoachingRelationship.receipt_templates` JSON-column precedent, since both are small, bounded, always read whole, and rewritten wholesale on every revision rather than queried on their own terms. `status` is `drafting`|`active`|`superseded`|`failed`; at most one active plan per user, held by the writer rather than a DB constraint (superseding is a two-row deactivate-then-insert transition, and a partial unique index is Postgres syntax the SQLite test database cannot exercise). The coach drafts the plan; there is no plan-builder form and none is planned: `POST /api/schedule/draft` (`services/schedule/store.create_drafting_plan`) writes an empty `drafting` row up front, enqueues `generate_schedule_job` (`app/jobs/generate_schedule.py`) on the worker, and returns 202, and `GET /api/schedule/draft` (`store.latest_plan`) is the status poll the client reads until the row moves; a `drafting` row is invisible to `store.get_active_plan`, so the week keeps serving the previous plan (or free mode) while a new one is written, and `store.draft_in_flight` is the idempotency guard a second `POST` while one is running returns rather than starting a second, excluding rows older than `store.DRAFT_STALE_AFTER` (15 minutes) so a crashed worker or dropped job cannot wedge the feature in `drafting` forever. `services/schedule/draft.py`'s `draft_plan` runs the generation as `TurnKind.SCHEDULE` (`coach/turn.py`, #830) through the metered `turn.build_client`, so it resolves to `COACH_MODEL_ID` (no dedicated model lane) and records its spend on the per-user budget counter like every coaching turn, gated by `turn.over_budget` before any call is made; the assembled context (`build_draft_context`) is the runner's profile, stated goal race, their own volume norm split all-activity vs running-only, the disciplines they actually train, current readiness, memory, and selected coaching school — never the coach report's context pack, since a plan answers "what should happen next" rather than "what just happened" and carries no stream data. A follow-up closed a gap owner review found: the race line in the context now states the race's own WEEK (`week_start(race.race_date, starts_on)`), and the system prompt instructs the coach to build the block BACKWARDS from that date — the peak far enough out to absorb it, the taper running into the race — and, when the race falls inside the horizon, to sketch the recovery weeks after it rather than stop dead at the finish line; measured on a real draft, phases moved from an ungrounded Base/Build/Peak to Build → Peak → Taper → race → Recovery. The running-only norm both `draft.py` and `week.py` read is now the one function `schedule/norms.py` defines (`running_norm_weekly_m`), replacing what had been a private copy inside `draft.py`. The coach answers by calling exactly one forced tool, `record_training_plan` (`draft_contract.py`), no free-form channel, coerced through strict Pydantic (`extra="forbid"`, every field bounded) — the ADR 0017 material-distiller containment spine applied to a second generative surface — with only the free-text `summary` normalised by truncation and every structural field left exactly as the model produced it or rejected outright. The key decision: the tool offers no field for training load at all — the coach says what a session IS (discipline, intent, and a distance, a duration, or a rep structure) and `effort.py`'s `estimate_effort` prices it from the runner's own history (`build_load_model`: median load per second, per metre, and per session over a 182-day lookback, abstaining below `MIN_SESSIONS_FOR_RATE` (3) samples for a discipline) — the North Star's hard case, a model reading a bare load number as an intensity verdict, applied to a generative surface rather than a pack field. `plan_validator.py`'s `validate_drafted_plan` is the deterministic COHERENCE gate a draft must pass before it is stored, not a coaching opinion: it checks week boundaries, no past weeks, no week given as both concrete and sketched, the configured horizon reach (`HORIZON_SLACK_WEEKS`, 2, past `SCHEDULE_HORIZON_WEEKS`), session placement windows, that every non-rest session carries a distance, a duration, or a rep structure, and — via a backtracking `check_rules` pass over the plan's own rules plus an implicit `max_sessions_per_day` floor (`ABSURD_SESSIONS_PER_DAY`, 4) the coach never has to remember to write — that each week's own rules admit at least one legal arrangement; its only volume check is an absurdity ceiling at twice (`MAX_WEEKLY_MULTIPLE`) the runner's own running norm, abstaining entirely when there is no norm to measure against, since there is no population ramp rule. A draft that fails coercion or validation is rewritten with the failures fed back into the prompt (two rewrites total) and a transport error gets one separate retry whose error text never reaches the prompt; exhausting both leaves `status="failed"` with nothing stored — a plan does not degrade the way a report can, since half a schedule is worse than none when the runner would act on it — and `generate_schedule_job` marks the row failed on any unhandled exception too. An accepted draft is persisted by `draft._persist`: each concrete session becomes a `PlannedSession` with `target_effort_score` priced by `estimate_effort`, each sketched week's `discipline_mix`/`intent_mix` are derived from the model's session counts against the same load model rather than asked of the coach (one number, one owner), and `store.activate_plan` makes the new plan active in the same transaction that supersedes its predecessor. A `PlannedSession` (#830) is the schedule's concrete unit, described along three independent axes that stay independent so one screen serves a rigid weekday plan, a loose floating week, and no plan at all: PLACEMENT, COMMITMENT (`committed`|`suggested` — a dismissed or lapsed suggestion is dropped from the week read and generates no follow-up, while a missed committed session is kept), and DISCIPLINE (`run`|`walk`|`bike`|`strength`|`row`|`other`, orthogonal to `intent`: an easy bike and an easy run are the same stimulus, so `intent` carries the reading and discipline is named alongside it). Placement has no column: a session stores an inclusive `[window_start, window_end]`, and `services/schedule/placement.py`'s `derive_placement` reads `pinned` from `window_start == window_end`, `week` from a window spanning the whole week, and `window` from anything between; the EFFECTIVE window is `max(window_start, today)..window_end`, computed at read time (`effective_window`), so a floating session narrows with no job running per session and the stored window never moves — "narrowed from Thu-Sat" is a stored-vs-effective comparison, not an edit history. `structure` (`{reps_planned, rep_distance_m, rest_s}`) is the shape `workout_matching.match_planned_to_detected` has been waiting for since the beginning, and `services/schedule/completion.py` (#830) is the slice that starts writing it and the row's completion columns (`completed_at`/`completed_activity_id`/`completion_source`, plus `dismissed_at`): ONE write, `complete_planned_session`, the `write_checkin` precedent — reached by three routes (an activity auto-matched on the ingest pipeline via `complete_from_activity`, a manual tap on `POST`/`DELETE /api/schedule/sessions/{session_id}/complete`, or the coach's `complete_session` proposed action once the runner confirms it) rather than three copies of what "done" means. The matcher (`find_matching_session`) is deliberately conservative — the active plan only, a window containing the activity's local day, a matching discipline, and the activity at least `MIN_COMPLETION_FRACTION` (0.5) of the session's target distance or duration, so a short jog cannot claim the long run — and ranks a committed session over a suggestion, then closeness to target, then the narrower window; `complete_from_activity` is idempotent on `completed_activity_id`, so a re-analysis or replayed webhook cannot double-tick. `find_matching_session` also feeds `workout_matching.match_planned_to_detected` (`_extract_planned_workout` in `services/analysis/_orchestrator.py`, resolved in `analyze`'s load phase as `StageContext.planned_session`): it no longer returns `None`, the placeholder it had been since the beginning of the project — `match_planned_to_detected` had never once been handed a plan, so its plan-scoring block, and with it the `compute_confidence` branch that appends the CRITICAL `interval_structure_mismatch` reason on `match_score < 0.7`, was unreachable through `analyze`; `tests/test_analysis_stages.py` pinned that dormancy so it would be revisited deliberately, and now pins the opposite. `POST /api/schedule/sessions/{session_id}/dismiss` declines a SUGGESTION only (`dismiss_planned_session`, 422 on a committed session — declining an agreed session is a plan change, which stays the coach's to make). Auto-completion runs in `process_new_activity_job` (`_autocomplete_planned_session`) after `analyze` and before the cadence speaks, guarded so a schedule fault never costs the runner their report; the Strava delete webhook path calls `clear_completions_for_activity`, which clears only `AUTO` completions for the deleted activity (`clear_completion`) and leaves a manual tap or a coach-confirmed one alone, since deleting a Strava upload does not unsay that the runner did the session. Spacing rules are a closed code-resident vocabulary of five kinds (`rest_day_after`, `no_intent_day_before`, `min_days_between`, `preferred_days`, `max_sessions_per_day`) with one pure predicate each (`services/schedule/rules.py`), checked by a backtracking constraint search (`find_assignment`/`check_rules`, smallest-domain-first) that answers "does a legal arrangement exist" — the honest question for a week whose sessions mostly have not been placed yet — rather than linting one placement; every predicate is monotone (adding a session can only add violations, never remove one), which is what makes pruning a partial assignment during the search sound. Migration `b7d2e4f19a83` (off head `a1c4e77b9d02`) adds all three tables; none alters an existing table and both FKs point only at `users`/`activities`, so it is inert against a still-old-code production.

Under the receipt cadence the keyboard also carries a `done` button whose tap records `Exchange.done_at` and schedules the full report (~`BLOCK_GAP_SECONDS`) via `mark_done_and_schedule`, writing no `CheckIn`.
User-triggered self-healing (`self_heal_job` in `app/jobs/self_heal.py`, #123/ADR 0006) discovers activities Strava webhook missed and converges on the same pipeline. It replaces the deleted time-based polling fallback, which could not survive multi-user (Strava's rate limit is per-application, so steady-state polling across many users exhausts the shared budget): instead an authenticated app-open or an explicit Refresh tap calls `POST /api/activities/refresh`, which enqueues ONE bounded per-user check (one Strava call on the worker) that diffs the runner's recent Strava activities against their stored history and enqueues `process_new_activity_job` for the gap. The check costs nothing when nobody is using the app, is bounded to at most one run per user per `SELF_HEAL_MIN_INTERVAL_SECONDS` via an atomic Redis key (so rapid taps do not multiply Strava calls), and the existing per-activity dedup (`Activity.coach_notification_sent_at` + a deterministic `job_id`) still guarantees once-only processing if the webhook and the self-heal race.
Deep processing classifies the activity, computes metrics from streams (smoothing, splits, intervals, stops, efficiency, risk), and runs workout matching against any planned workout.
The coach pipeline builds a context pack, calls Anthropic, validates the response against a Pydantic schema, then runs a deterministic policy validator before storing the report; LLM/parse failures persist a fallback `CoachReport` with `is_fallback=True`.
The coach output has two shapes keyed by prompt family (ADR 0009, A3): the legacy structured `CoachReportContent` (schema 1.2, `coach_report_*` prompts) and the A3 prose `CoachMessageReport` (schema 2.0, `coach_message_*` prompts) — a human prose `message` written before any structure (adaptive thinking → message → one strict-tool tail carrying `headline`/`next_steps`/`risks`/`questions` with typed `TappableOption`s), stored in the same `coach_reports.report` JSON column (no migration); `service.active_schema_version(prompt_id)` resolves the cache identity from the prompt-id prefix (`SCHEMA_VERSION_BY_FAMILY`), so cutover and rollback are each a pure `COACH_PROMPT_ID` config flip. `get_or_generate_coach_report` dispatches on family to `_generate_structured` or `_generate_message` (the A3 single call `llm.generate_coach_message` + the `output_contract.py` parse/merge); the prose path degrades-not-withholds (a real message survives a missing/unusable tail as `tail_degraded=True` with empty `next_steps`, the loop then abstains) and a medical-overreach violation surviving the policy retry forces `is_fallback=True` (the one A3 strengthening, since prose renders verbatim). The tail's `next_steps` land at the same JSON key/shape `retrieval.fetch_prior_commitments` reads, so the M7 adherence loop survives the cutover by construction; `digest.py` projects the message's first sentence as the digest lead. The code config default is `coach_message_v8` (`core/config.py`); production runs `coach_message_lean_grouped_v9` (the ADR 0026 grouped-pack prompt carrying both the #742 BODY and the #830 SCHEDULE capabilities, flipped live 2026-08-12 from `coach_message_lean_grouped_v7`, rollback = `coach_message_lean_grouped_v7`, or `coach_message_lean_grouped_v8` to back out SCHEDULE while keeping BODY); the vN chain reached v14 via the #266 v8 flip 2026-06-18, then the v9 volume, v10 stream-view (#443), v11 recent-training (#444), v12 training-history (#561), v13 runner-memory (ADR 0025), and v14 intensity-distribution (#578, flipped 2026-06-30) flips, with `COACH_RECEIPT_CADENCE` on throughout.
The context pack carries a `block` section (A1) ONLY for a multi-member block: the chronological member list (type/duration/distance, primary marked) plus combined totals, built by `_build_block_context` in `context.py` so the coach can speak about the morning as a whole; a block-of-one emits no key at all and its pack is byte-stable against the pre-A1 shape (AC8, pinned by test — `to_serializable_dict` drops the null field). Novelty, digests, baselines, and the M4-M10 learning loop stay activity-level through the primary activity.
The context pack carries a `longitudinal` section (M4): a token-bounded digest of the runner's last 1-2 non-fallback reports (date, headline, `lead_argument`, recommended `next_steps` only, never the full body) plus the matching `RunnerBaseline` bucket trend for this run's `effort|terrain|temp-band` context (omitted while that bucket still abstains), so the report advances the prior narrative instead of restating it.
The context pack also carries a `perceived_effort` section (M6, computed by `services/coach/perceived_effort.py`): the gap between the runner's subjective `CheckIn.rpe` and the HR-derived `effort` axis (a signed 1-5-band divergence; divergence is computed against the intensity axis, not the cumulative TRIMP-like `effort_score`, which is carried raw), a `recommended_weighting` that favours RPE over HR when an N4 `discount_signals` confounder fired (RPE survives HR distortion), and a `pain_trend` over recent check-ins (abstains under `MIN_PAIN_SAMPLES`, never a diagnosis); it degrades to nulls when no check-in exists. One-fact-one-place fold (`coach_context.to_serializable_dict`): the analytical sections that restated a raw scalar already homed elsewhere have that copy DROPPED from serialization — `perceived_effort.rpe` (→ `check_in.rpe`), `perceived_effort.effort_score` (→ `metrics.effort_score`), `calibration.hr_drift.observed_drift_pct` and `metrics.discount_signals.hr_drift_pct` (both → `metrics.hr_drift`) — so each fact reaches the coach once; the builders still populate the model objects (the derived reads compute from them), the dropped fields are Optional/freeform so stored pre-fold packs still validate, and the M5 eval's discounted-inflated-HR rubric reads the drift from `metrics.hr_drift`.
The context pack also carries an `adherence` section (M7, the "gets better over time" loop, pure logic in `services/coach/adherence.py`, gathered by `_build_adherence_context` in `context.py`): for each `next_step` in the most recent prior non-fallback report, a `NextStepOutcome` labelling the runner's subsequent comparable activity `acted_on`/`ignored`/`contradicted` (or `disputed` when overridden), re-derived on demand from the already-stored `Activity`/`DerivedMetric` rows (no durable store; the retired M8 belief store no longer backs it, and under ADR 0025 the outcome is consumed under the v13 non-nag discipline). A step abstains (no outcome) unless it maps to a recognised theme (`easy_discipline`, `add_quality`, `add_long_run`), survives a negation/caution guard (so "hold off on adding intensity" is never read as "add intensity"), has a comparable non-low-confidence run to judge against, and (for the window themes) the runner has had `_MIN_OPPORTUNITY_RUNS` comparable runs before a miss is called `ignored`. Easy-discipline excludes races, detected interval sessions, and declared workouts from comparability, and only asserts the strong `contradicted` when the run's `user_intent` was explicitly easy (an unlabelled hard run is softened to `ignored`, since this single-user dataset carries no intent labels and a hard run may have been deliberate). An explicit `CheckIn.notes`/`CoachChatMessage` pushback on the prior report flips the implicit label to `disputed`, which the prompt treats as settled (says nothing), so a false-positive pushback only suppresses a note. It degrades to empty (the coach then says nothing about adherence) when there is no prior report.
The context pack's always-present `profile` section also carries a nested `body` sub-field (#742, the runner's stated build): `weight_kg`/`height_cm` read straight off `UserProfile` by `_build_body_context` in `context.py`, gated by `PromptFeature.BODY` and dropped byte-stably via the `profile` signal's `nested_drop=drop_profile_body` (one `signal_registry` row since #800, which derives that descriptor along with the section's group and flat position) — the `corpus.user_materials` nested-drop idiom, so under every prior prompt the profile section is byte-identical to its pre-#742 shape (`profile` itself is never None, so that descriptor exists purely to carry the nested trim). It abstains entirely when the runner has stated neither figure, because null is NOT average: absent means the coach is never invited to fill the gap with a typical runner. Deliberately raw facts only — no BMI or any derived index is stored or computed anywhere, since a ratio is the population formula the North Star's "coach this runner, not the median" exists to refuse; the build steers METHOD (ramp rate, run-to-strength ratio, recovery) and is never itself the advice, a boundary held by the grouped_v8 BODY prompt clause and the `body_not_made_the_subject` eval sensor (validator rule 5 does not reach weight-loss advice). Existed as a capability gap until #742: an A/B probe under grouped_v7 showed a "~109 kg" note in free-text `injury_notes` produced a substantively identical report.
The context pack also carries a `memory` section (ADR 0025/M3, the runner memory profile surfaced WHOLE — no retrieval/ranking/top-k): the runner's stored `RunnerMemoryProfile` five sections, built by `_build_memory_context` in `context.py` through the `ReadTimeSignal` seam from `memory_store.get_memory`, tier-tagged as the citable `Stated memory` tier that yields to this run's re-derived `DerivedMetric` on a factual conflict and never lowers the safety floor; it carries no behavioral verdict. Gated by `is_memory_prompt` (the `block`-section Optional-and-drop idiom) AND the `COACH_MEMORY_ENABLED` kill switch, dropping byte-stably (cold start, an empty/un-graduated profile, an off-shape stored row, or the switch off) so the pack stays byte-stable under every non-v13 prompt. The retired M8 `believed_facts`, M10 `preference_profile`, and A2c `narrative` pack fields are kept as never-populated Optional deprecated stubs so pre-v13 stored packs still validate under the pack's `extra="forbid"`.
The context pack also carries a `calibration` section (M9, pure logic in `services/coach/calibration.py`, gathered by `_build_calibration_context` in `context.py`): `hr_drift` reads this run's HR drift against the runner's own typical drift for the matching `effort|terrain|temp-band` bucket (computed at read time from prior comparable runs, since the RunnerBaseline is recomputed after the pipeline), marking `calibrated` true with an `above`/`below`/`in_line` comparison once `MIN_SAMPLES_FOR_CALIBRATION` (4) comparable runs exist, else falling back to the labeled population ~5% drift heuristic; and `referral`, a non-diagnostic clinician nudge fired only on computable red-flag patterns (the `illness_or_extreme_fatigue` flag, or sustained notable pain across recent check-ins), templated to pass the medical-scope validator and abstaining otherwise. Neither overrides the re-derived `DerivedMetric`.
The context pack also carries a `training_load` section (P3, ADR 0016, pure logic in `services/readiness.py`, gathered by `_build_training_load_context` in `context.py`): our own deterministic read of the runner's current condition — `fitness` (chronic load, a 42-day EWMA of `effort_score`), `fatigue` (acute load, a 7-day EWMA), `form` (their balance), a `ramp_rate`, and a labelled `condition`/`trend` — computed at read time (mirroring M9 calibration) over a windowed (`READINESS_WINDOW_DAYS` 182) EWMA-seeded daily load series as of the activity's `start_date`, so this run is in the acute load and per-read cost stays flat as history grows (#167). It is a tier-3 deterministic FACT the coach may cite (unlike the voice-only `narrative` or judgment-only `corpus`) but never overrides the run's re-derived `DerivedMetric` or the safety floor (prompt rule 27); while history is shorter than the chronic window it reads `warming_up` and the condition abstains (`building_baseline`). Emitted ONLY under a training-load-aware prompt id (`prompts.TRAINING_LOAD_PROMPT_IDS`/`is_training_load_prompt`, the `corpus`/`stance`/`block` Optional-and-drop idiom, so the pack stays byte-stable elsewhere). Platform numbers (Strava Fitness/Freshness, Garmin Training Load) are validation-only, never authoritative and never a cold-start seed (a different unit).
The context pack also carries a `training_volume` section (#400, pure logic in `services/coach/volume.py`, gathered by `_build_training_volume_context` in `context.py`): the frequency-/volume-vs-norm read answering "is this week up, down, or normal for me", so the coach reads a deliberate easy week as intentional rather than alarming. For each of four metrics (`sessions`, `distance_m`, `moving_time_s`, `effort_score`) it reports the current window value (holistic `current_all` across every logged activity plus a `current_runs` runs-only figure, so a walk is never read as a run) against the runner's norm (`norm_weekly` over a 12-week baseline and `norm_weekly_recent` over 4 weeks, each the runner's own clamped per-day training rate projected to a week, computed over history BEFORE the current 7 days; #451 standardized this on the SAME per-day-rate definition the Trends page and the `recent_training` section use, so "typical" means one thing across the product and a short or gappy history is not deflated by dividing it across weeks the runner had not started training), with a `direction` label (up/in_line/down/no_norm, ±15% deadband). Two framings ride the section: `rolling_7d` (trailing 7 days, directly comparable) and `calendar_week` (the current Mon-Sun block to date, judged against a norm pro-rated to `days_elapsed`); `has_baseline` is false (every direction `no_norm`) when history is too thin. One-lane-per-fact fold: in the coach pack, under a recent-training-aware prompt (v11+), the `rolling_7d` window DROPS its `current_all`/`current_runs` at serialization (it spans the same trailing 7 days as `recent_training.last_7d`, so those totals were a second copy of that section's roll-up/by_type), carrying the vs-norm VERDICT only (norm + `direction` + `pct_vs_norm`); the trailing-7d numbers live once in `recent_training`, and `calendar_week` keeps its current values (no counterpart elsewhere). The drop is GATED on `recent_training` being present, so a v11→v9/v10 rollback (no descriptive lane) keeps `rolling_7d`'s current values rather than losing them. The builder still computes current on both windows (direction/pct derive from it); the drop is serialization-only (`coach_context._drop_training_volume_rolling_current`), so `build_training_volume` and the Trends-page `build_volume_report` are untouched, and the fields are Optional so pre-fold stored packs still validate. Computed read-time over the runner's LOCAL-day windows (#399) as of the activity. A deterministic FACT the coach may cite but never overriding the run's re-derived `DerivedMetric` or the safety floor (the v9 VOLUME addendum); emitted ONLY under a volume-aware prompt id (`prompts.VOLUME_PROMPT_IDS`/`is_volume_prompt`, the Optional-and-drop idiom, byte-stable elsewhere — v9-minus-`training_volume` equals v8). The coach pack always uses the fixed this-week framing; the Trends-page `GET /api/trends/volume?range=` endpoint reuses the same pure core (`build_volume_report` in `volume.py`) but GENERALIZES to the runner-selected range — rolling `N` days plus the current calendar period (week/month/quarter/half/year) for 7D/30D/3M/6M/1Y, with the norm scaled per-day to the window — so the coach and UI share one computation without drift. Under the #451 consolidation this section is the weekly vs-norm VERDICT lane, paired with the descriptive `recent_training` section (v11, #444) that owns the modality + horizon read; the coarse legacy `recent_training_summary` is retired (no longer populated or serialized, kept only as an Optional schema field so pre-#451 stored packs still validate under the pack's `extra="forbid"`).

## Important Constraints

Settings come from `backend/.env` via `pydantic-settings`; `DATABASE_URL` is required and the app will not boot without it.
Anthropic access requires `ANTHROPIC_API_KEY`; the coach model id and prompt id are configured via `COACH_MODEL_ID` and `COACH_PROMPT_ID` (conversational turns — the activity chat box and thread turns — take `COACH_CHAT_MODEL_ID` when set, else `COACH_MODEL_ID`, #766; the #822 voice rewrite takes `COACH_VOICE_MODEL_ID` when set, else `COACH_MODEL_ID` — its own lever because the rewrite never sees the context pack, so it costs roughly a fifth of a report's input and the model choice is a quality decision rather than a cost one: a Haiku-class model holds the rewrite CONTRACT but flattens the CHARACTER) (code default `coach_message_v8`; production runs `coach_message_lean_grouped_v9` with `COACH_RECEIPT_CADENCE` on, rollback = `coach_message_lean_grouped_v7`). Flipping `COACH_PROMPT_ID` to `coach_message_v2` (or `coach_message_v3` the P1.1 voice-aware variant, `coach_message_v4` the P1.2 corpus-aware variant, `coach_message_v5` the P1.3 stance-aware variant, `coach_message_v6` the P3 training-load-aware variant, `coach_message_v7` the P4 user-materials-aware variant, `coach_message_v8` the #266 philosophy-retuned variant, `coach_message_v9` the #400 volume-vs-norm-aware variant, `coach_message_v10` the #443 stream-view-aware variant, `coach_message_v11` the #444 recent-training-aware variant, `coach_message_v12` the #561 training-history-aware variant, `coach_message_v13` the ADR 0025 runner-memory-aware variant, `coach_message_v14` the #578 intensity-distribution-aware variant, `coach_message_lean_v1` the disposition-first lean rewrite, `coach_message_lean_grouped_v5` the ADR 0026 grouped-pack prompt, `coach_message_lean_grouped_v6` the #712 past-session-laps variant (inert), `coach_message_lean_grouped_v7` the #743 personalisation variant, `coach_message_lean_grouped_v8` the #742 body-aware variant (inert), or `coach_message_lean_grouped_v9` the #830 schedule-aware variant (live in prod)) activates the A4 two-stage Exchange; any other (single-shot) id serves the prior path with zero code change. `COACH_RECEIPT_CADENCE` (bool, default off, #296/ADR 0018) is orthogonal to `COACH_PROMPT_ID`: when on AND the active prompt is two-stage it replaces the debounced LLM opener + 3h fuller timer with an instant deterministic per-activity receipt plus one full LLM report ~`BLOCK_GAP_SECONDS` after the session (the full report reuses the configured prompt's fuller mode, so cadence and prompt content roll back independently); inert under a single-shot prompt. Eleven orthogonal coach-input kill switches (#522, all `COACH_*_ENABLED` bools defaulting True = current behaviour, so the default code path stays byte-stable) each REMOVE one named item from what the coach receives and grey its UI input, reachable by setting the flag False in the environment (the COACH_PROMPT_ID/COACH_RECEIPT_CADENCE precedent): `COACH_USER_MATERIALS_ENABLED` (drops `corpus.user_materials`), `COACH_RELATIONSHIP_ENABLED` (stops reading `coaching_relationship` so voice + stance resolve to defaults and receipt voicing falls to the house floor), `COACH_HOUSE_SCHOOLS_ENABLED` (drops `corpus.school`, retaining HOUSE_CORE), `COACH_LONGITUDINAL_ENABLED` (drops the whole `longitudinal` section), `COACH_PLAYBOOK_ENABLED` (no activity-type playbook in the system prompt), `COACH_VOICE_BLOCK_ENABLED` (off = the runner's voice is not applied: since #822 that means the voice REWRITE pass never runs, so every runner reads the voiceless baseline, and the rendered voice block is still withheld from the conversational turn that continues to steer at prompt time), `COACH_STOPS_ANALYSIS_ENABLED` (drops `metrics.stops_analysis` for the coach; the pipeline still computes + stores it for risk/flags), `COACH_SLEEP_QUALITY_ENABLED` (drops `check_in.sleep_quality` for the coach; `risk.py`/`flags.py` keep their null-defaults), `COACH_SALIENCE_ENABLED` (drops the `salience` section; the fuller-turn scheduling is untouched), `COACH_CONTINUITY_ENABLED` (drops the `continuity` section), and `COACH_PREVIOUS_30D_ENABLED` (drops the `previous_30d` window from `recent_training`, leaving the vs-prev reads intact); whole sections drop byte-stably via the `PACK_SECTIONS` registry, nested fields gate to None. ADR 0025 adds a twelfth coach-input switch in the same family, `COACH_MEMORY_ENABLED` (default True; drops the `memory` pack section AND disables the runner-memory update writer), so the whole memory substrate ships behind one flip. `COACH_THREADS_ENABLED` (#784, default True) is the thirteenth and the only one that gates a SURFACE rather than an input: off, every `/api/coach/threads` route refuses with 503 (a router-level dependency, so a route added later cannot forget it) and the frontend renders no launcher, sheet, or conversational report options — the fastest lever if the coach's proposed actions (its first self-initiated write path) or a coaching skill misbehave, since the alternative is a revert and a redeploy. Off hides the conversation without deleting it: stored threads, the activity-scoped `GET`/`DELETE /coach-chat` history read, the report pipeline, receipts and notifications are all untouched, and a refused turn writes no row. The ADR 0025 runner-memory update job's model is `claude-haiku-4-5`, hardcoded by design (no config knob): it is a rewrite-from-source task; the #296 offline receipt-voice generator (`generate_receipt_templates_job`) is likewise hardcoded `claude-haiku-4-5` (a cheap style task). All three auxiliary Haiku paths (the material distiller, the runner-memory update job, and the receipt-voice generator) record their token spend on the per-user budget counter (`budget.record`, #472) so the global cost counter is honest; they keep their own explicit record calls and a SOFT entry gate (#607: a background distill/memory-update/voice-refresh pauses rather than hard-failing), and `record` is a safe no-op when budgets are unconfigured. The four COACHING turns (report/opener/fuller/thread) instead record via the `turn.MeteredClient` they are handed (#801), so recording is a property of the client rather than something each call site must remember — which is what #786 was: the thread turn checked the cap and never recorded against it, so the product's most token-hungry path spent unmetered, and the legacy structured report family had the same gap. Usage rides a `*_with_usage` sibling on the Anthropic client (`generate_structured_with_usage`/`generate_text_with_usage`), leaving the plain `generate_structured`/`generate_json`/`generate_text` wrappers byte-stable for their existing callers.
`SCHEDULE_ENABLED` (#830, bool, default True) is the schedule surface's own kill switch, the `COACH_THREADS_ENABLED` precedent applied to a product screen rather than a coach input: off, every `/api/schedule` route refuses with 503 (a router-level dependency, so a route added later cannot forget it) and the frontend renders no Schedule tab; stored plans, sessions and races are untouched. Deliberately NOT `COACH_`-prefixed and NOT part of the `/api/coach/feature-flags` map, since that map is the enabled-state of coach INPUTS and this gates a screen rather than an input; the orthogonal coach-input switch, `COACH_SCHEDULE_ENABLED` (#830 final slice, default True), IS on that map (as `schedule`) and IS wired: it is the kill switch on the `right_now.schedule` `CoachSignal` row, applied by `read_time_signals.gather` with effect `drop` — off, the coach stops seeing the runner's plan while the schedule screen keeps working exactly as before. `SCHEDULE_HORIZON_WEEKS` (#830, default 12) and `SCHEDULE_CONCRETE_WEEKS` (#830, default 3) are inputs to the drafting prompt as well as the horizon read — concrete sessions for the near weeks, shape only beyond — so changing either changes what the coach is asked for and not only what is displayed.
The A4 two-stage Exchange cadence is configured via `EXCHANGE_STAGE2_DELAY_SECONDS` (default 10800 / 3h, the fuller-turn timer fallback fired via RQ-native `queue.enqueue_in`) and `EXCHANGE_REPLY_WINDOW_SECONDS` (default 86400 / 24h, how long after the opener a reply still triggers the fuller turn early); both are inert under a single-shot prompt. `RQ_JOB_TIMEOUT_SECONDS` (default 600, #264) is the RQ death-penalty ceiling for worker jobs: a two-stage coach generation runs ~120-360s, past RQ's 180s default, so a slow fuller turn / regeneration was being killed mid-write before storing its report; it is applied as the queue `default_timeout` (all `queue.enqueue` paths, which the deferred `queue.enqueue_in` jobs inherit) and as the explicit `job_timeout=` on the RQ-native `queue.enqueue_in` calls (block-complete opener, scheduled fuller turn; RQ-native uses `job_timeout`, not rq-scheduler's `timeout`, #123).
`BLOCK_GAP_SECONDS` (A1, default 1800 / 30min) is both the block grouping threshold and the block-complete debounce that gates the opener, so a solo run's opener arrives ~30 minutes after processing rather than instantly (a deliberate ADR 0011 trade); block ASSIGNMENT runs under every prompt (the data model is always on), while the block-complete opener trigger is two-stage-only.
Coach-report notifications pick a channel by config (`_active_channel` in `app/services/notifications/__init__.py`): Telegram when `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` are both set, else a no-op. The self-healing check bound is `SELF_HEAL_MIN_INTERVAL_SECONDS` (default 60s, #123/ADR 0006): at most one per-user Strava check per this interval (atomic Redis SET NX EX), so app-open spam and rapid Refresh taps collapse to one call. The check looks back a fixed 7-day window (a module constant, not a setting) for missed activities; a gap older than that is closed by a manual `POST /api/sync` backfill.
The historical stream backfill is paced by `BACKFILL_BATCH_SIZE` (default 20, activities per batch) and `BACKFILL_BATCH_PAUSE_SECONDS` (default 300, delay before the next batch); the default 20 stream calls per 5 minutes stays under Strava's 100-requests/15-min ceiling, and because the backfill is one-time its daily cost is just the backlog size and converges to zero.
The historical Strava import (#239) is paced by `IMPORT_PAGE_SIZE` (default 50, activities per Strava page) and `IMPORT_BATCH_PAUSE_SECONDS` (default 5); each batch is a single Strava list call (no per-activity stream calls), so the call rate stays well under the 100-requests/15-min ceiling and the short pause only yields the single worker to webhooks between pages.
The bulk history re-analysis (#300) is paced by `REANALYZE_BATCH_SIZE` (default 100, activities per batch) and `REANALYZE_BATCH_PAUSE_SECONDS` (default 5, delay before the next batch); unlike the stream backfill the pacing is not rate-limit driven (re-analysis is local compute from already-stored streams, no Strava calls), so the batch is large and the pause short — it only yields the single worker to webhooks between batches.
CORS origins are configured via `CORS_ALLOWED_ORIGINS` (comma-separated, default `http://localhost:3000,http://localhost:8000`), parsed by `Settings.cors_allowed_origins_list` and applied in `app/main.py`.

The deterministic policy validator in `services/coach/validator.py` has seven rules (the A2c narrative-is-not-evidence rule 6 was RETIRED with the narrative in M4/ADR 0025; the remaining rules keep their original 1-8 numbering with 6 skipped): it rejects LLM output that misses questions for a null check-in, references uncalibrated HR zones, cites a risk flag not in the flags array, claims specific interval execution counts (e.g. "8x400m", "executed 8") under low detection confidence, (the medical-scope rule) gives dose advice, uses diagnosis verbs, issues directive medication advice, or asserts a clinical condition about the runner (while still permitting interpretive metric correction and a non-diagnostic referral nudge), (the P1.2 corpus-is-not-evidence rule) cites a `corpus.*` field path as report evidence — the coaching corpus is judgment knowledge the coach reasons from and can never ground a factual claim, and (the P4 user-materials-is-not-evidence rule) cites a `corpus.user_materials.*` field path as report evidence — the runner's uploaded materials are judgment reference the coach reasons from (they outrank house philosophy for stance) and can never ground a factual claim (the corpus and user-materials rules are deliberately narrow: they match only their own section path, so they never force a false-positive fallback; the ADR 0025 runner memory profile deliberately gets NO such rule because it is the grounded, citable `Stated memory` tier); per `ai-workflow.md` this gate must not be bypassed. The seven rule bodies are shared `check_*` functions over primitives (a text surface, structured flags/questions, evidence paths, pack facts), assembled by `validate_policy` from the structured report and by `validate_message_policy` (A3) from the prose `message` + tail, so both output shapes are policed by one identical rule set; the message entry point polices the full prose plus every tail text field (including tappable-option labels), and the service forces `is_fallback=True` when a medical-overreach violation survives the retry on the prose path. Streamed conversational output is policed by the same shared rule bodies (#340) through `validator.validate_conversational_policy`, the third assembly of those bodies and, since #801, the only one that used to live outside `validator.py` (`chat._validate_conversational_text` is retained as an alias; the floor's behaviour is unchanged, ADR 0024): `chat.py` assembles the full reply before any of it is sent (a streamed token cannot be un-sent, and token boundaries do not align with the rule patterns) and runs the text-surface rules that bind to free-form prose — medical-scope (rule 5, the hard floor, pack-independent) plus uncalibrated-zone (rule 2) and ungated-interval (rule 4) when the stored context pack parses; a medical overreach withholds the raw reply and serves a safe non-diagnostic redirect (`MEDICAL_REDIRECT_MESSAGE`, the chat analogue of the report's forced fallback, itself written to pass the validator), while soft violations are logged and let through, then the validated reply is re-streamed in slices so the typing effect survives. Because that buffering leaves a silent gap between the route's `: ok` frame and the post-generation content (where token streaming used to keep bytes flowing), `_buffered_tool_loop` yields content-free heartbeats throughout buffering that the route renders as SSE comment frames (`: hb`, ignored by the client), keeping the proxy connection alive so an idle timeout cannot sever the stream mid-reply (#375).
When data confidence is low, downstream analysis is expected to default to conservative output (documented intent in `README.md`).
Postgres is exposed on host port `5433` (mapped from container `5432`); Redis on `6379`; backend on `8000`; frontend on `3000`.
Backend test baseline excludes tests marked `integration` (pytest marker registered in `pyproject.toml`).

## Architecture Summary

The backend is a FastAPI app (`app/main.py`) wiring routers from `app/api/*` under the `/api` prefix.
Persistence uses SQLAlchemy 2.x ORM with a Postgres database; schema migrations live under `backend/alembic/versions/`.
Background work runs via Redis-backed RQ; jobs are defined in `app/jobs/` and the worker entrypoint is `python -m app.worker`, which runs `worker.work(with_scheduler=True)` because RQ's worker-embedded scheduler thread drains BOTH interval retries and all deferred `queue.enqueue_in` jobs (block-complete opener, fuller-turn timer, backfill/reanalyze/import batches) from the ScheduledJobRegistry (locally `rq worker --with-scheduler`). There is no separate scheduler process: the time-based polling fallback and its `rqscheduler` process were removed (#123/ADR 0006), and every deferred job now rides RQ-native scheduling on the worker.
The Strava integration is a port (`StravaPort` in `app/services/strava_ingestion/port.py`) with `HTTPStravaAdapter` and `InMemoryStravaAdapter`; on top of that port the package splits its concerns into `ingestion.py` (the batch orchestrators), `persistence.py` (the Activity/stream writer), `auth.py` (token refresh + per-account lock), and `zone_sync.py` (HR-zone calibration), while block grouping/recovery lives in `blocks.py` and the zone parser + lap-preservation rule live with the analysis they serve (ADR 0002, ADR 0003, #702).
The port also exposes `get_athlete_zones`; `zone_sync.sync_athlete_zones` + the pure `analysis.zones.extract_hr_zone_bounds` parser store the runner's five HR-zone lower bounds on `UserProfile.hr_zones` during sync, and `_orchestrator` threads them into `metrics.calculate_time_in_zones` (#297).
Analysis is a pipeline of pure-ish functions in `app/services/analysis/` (smoothing, metrics, classifier, splits, intervals, stops, flags, risk, discount signals, workout matching) composed by `_orchestrator.py`; the public surface is `analyze` and `analyze_with_streams`. The stage SEQUENCE is data rather than placement in the function body (#805): `stages.py` holds the `ANALYSIS_STAGES` registry of thirteen `Stage` descriptors, each naming what it READS and what it WRITES, and `assert_stage_contract` runs AT IMPORT (mirroring the `PACK_SECTIONS` registry's import-time check) so a stage reading a field no earlier stage writes is a startup `RuntimeError` rather than a quietly wrong row — the three ordering invariants that used to live only in comments (probe-before-classify, the structure axis gating the interval-only stages, and the coverage of every analytical column) are now checkable declarations. The declarations are self-enforcing at run time: `StageContext.get` raises on a read the stage did not declare and `run_stages` raises on a write it did not declare, so an under-declared stage cannot hollow out the import-time check. Each stage receives a projection of exactly its declared reads (the flags stage takes five fields, not the whole 23-field accumulator), the stage functions themselves are untouched, and every stage — including the four formerly imported lazily inside the function body (`build_training_context`, `compute_discount_signals`, `build_stream_view`, `recompute_runner_baseline`) — resolves through the `_orchestrator` module namespace, the single seam the composition tests patch. One ordering constraint stays prose because the read/write graph cannot express it: the post-commit runner-baseline recompute is ordered against the COMMIT, not against another stage's output. The upsert still writes all 23 columns unconditionally, so a stage that abstains overwrites the prior value — surfaced, deliberately unchanged, since altering it is a behaviour change and not a refactor. The interval-structure stage (`intervals.py`) has two sources behind one `interval_structure` contract: `detect_intervals_from_laps` reads the runner's recorded Strava laps from `raw_summary` (their own lap-button marks) as the authoritative segmentation and takes precedence when the laps show a clear bimodal work/rest pattern, tagging the structure `source="recorded_laps"`; `detect_intervals` (the velocity-stream smoothing + bimodal heuristic) is the fallback when no usable laps are present (#170). Lap-sourced structure skips the stream heuristic's smoothing, minimum-duration, and 120s-warmup floors (so a short recorded warmup or short reps are reported as marked) and yields `workout_match.detection_confidence="high"` since the structure is ground truth rather than inferred; the classifier still gates `structure=="intervals"` on `pace_variability` plus a probed structure, so an auto-1km-lapped easy run is not turned into an interval session. A zero-speed standing/autopaused recovery lap is read as rest (the strongest work/rest signal) rather than aborting the lap path, and `compute_confidence` skips its stream-era sanity checks (`work_time_implausibly_high`, `no_warmup_detected`) for `source="recorded_laps"` so ground-truth structure is not contradicted by a low-confidence reason; `upsert_activity` preserves an existing row's recorded `laps` when a lap-less summary payload re-syncs the activity, so a routine manual `POST /api/sync` (summary list endpoint, no laps) does not clobber detail-ingested laps and silently downgrade the lap-sourced structure back to the stream heuristic. The discount-signals stage (`discount_signals.py`) is a deterministic, pipeline-owned annotation marking when HR drift is likely inflated by heat (`average_temp` from `raw_summary`), terrain (`is_hilly`), or the opt-in `UserProfile.stimulant_use` flag, so the coach discounts it rather than reading it as fatigue; it only fires when the drift is actually elevated (above `ELEVATED_DRIFT_THRESHOLD_PCT` 5%, mirroring the `flags.py` fatigue threshold) so a confounder on a negligible-drift run yields no discount instruction (#176); it degrades gracefully and never fabricates a confound. The consolidated-stream-view stage (`stream_view.py`, A2a processed-artifacts layer) runs after metrics and before the `DerivedMetric` upsert: `build_stream_view` produces a bounded (<=60 points), index-aligned, shape-preserving downsample of HR/pace/grade/cadence from the same `streams_dict` (pace derived from velocity and null when stopped, cadence series-mean-normalised to spm), stored on `DerivedMetric.stream_view` (a deferred-load JSON column so the common `activity.metrics` load stays lean and the view is pulled only on demand) and re-derived every analysis; it degrades to null without streams.
The coach layer is `context.py` (assembles the working context — a lean always-present `B baseline` plus the subject activity's `focus payload`, via `build_b_baseline`/`build_focus_payload` composed by `assemble_working_context`, A2b — and flattens it into the pack, byte-identically to the prior one-pass builder) → `llm.py` (Anthropic client) → Pydantic schemas in `app/schemas/coach.py` → `validator.py` (policy gate; `validate_policy` for the structured shape, `validate_message_policy` for the A3 prose shape, both over the shared `check_*` rule bodies) → `service.py` (dispatches on prompt family to `_generate_structured`/`_generate_message`, the A3 prose call going through `llm.generate_coach_message` + `output_contract.py`; caches result in `CoachReport`, with `is_fallback=True` on LLM/parse failure or surviving prose medical-overreach; also stores the A2a exchange digest on `CoachReport.digest` for non-fallback reports via the shared `digest.py` projection, so the stored digest is byte-equal to the longitudinal read) → `voice_rewrite.py` (#822, the last stage: the finished prose is said again in the runner's declared voice). The report is generated VOICELESS — `build_system_prompt` no longer takes or appends a voice — and the rewrite may re-word and re-emphasise the settled text but may not introduce a fact, drop a safety item, or change a verdict, so voice shapes delivery with no route to the substance. Both survive: the voiceless baseline stays `CoachMessageReport.message`/`opener_message` (what the digest, the eval harness and the learning loop read, since they consume substance) and the voiced rendering lands in `voiced_message`/`voiced_opener_message` (what the runner reads, and what the notification renders via `_prose.runner_facing_prose`); the two-stage split is mirrored because one evolving row would otherwise let the fuller turn overwrite the opener's voiced prose. Every failure — default voice, kill switch, over budget, transport error, an invented number, or a policy violation the baseline did not already carry — resolves to serving the baseline, so a style pass can never cost the runner their coaching. `output_contract.py` (A3) owns the hand-frozen `record_coach_tail` strict-tool JSON, the order-agnostic block parser, and the degrade-not-withhold merge into `CoachMessageReport`. The A2b retrieval seam (`retrieval.py`) pulls A2a's stored processed artifacts on demand: `fetch_stream_view` loads the deferred `DerivedMetric.stream_view` only when an activity is deep-dived (the default report path never loads it), `fetch_prior_digests` reads the stored `CoachReport.digest` (falling back to re-projecting via `digest.py` for pre-A2a rows) for the longitudinal last-exchange memory, `fetch_recent_user_digests` pulls a runner's most recent exchange digests user-scoped (the input the ADR 0025 runner-memory update writer re-grounds the profile from, for `lately` thread-state only), and `fetch_prior_commitments` (A2d) pulls the single most recent prior non-fallback exchange's structured `next_steps` + source-activity ref from the stored exchange record, the machine-readable commitments the M7 adherence loop judges later runs against (so `_build_adherence_context` reads through the seam instead of re-querying and carrying the full report body in `context.py`). The read-time history-scan signals `context.py` gathers (calibration, adherence, training_volume, training_load/readiness, recent_training, training_history, the ADR 0025 `memory` profile read, the #578 `intensity` read, and the #830 `schedule` read) are reached through one `read_time_signals.py` `ReadTimeSignal` seam (#492): each is an adapter with a `(db, activity, as_of) -> section | None` compute, and `gather` applies the prompt-feature gate plus thin-history abstention once, leaving room for #203's stored-artifact adapter (a read-stored compute re-registered under the same signal name) with no `context.py` change. The byte-stable-drop wiring (a gated-off section emits no key, never a null key) is data: `PackSection` descriptors in `app/schemas/coach_context.py` (#493) pair each declared `CoachContextPack` field with its feature gate and an optional nested-drop post-processor, `to_serializable_dict` iterates `PACK_SECTIONS` rather than seven hand-copied branches, and an import-time `_assert_descriptors_match_fields` check fails loudly on a descriptor naming an undeclared field. #800 makes that registry — and the flat order, the group map, the read-time signal wiring and the grouped-prompt id set — DERIVED VIEWS over ONE declaration: `services/coach/signal_registry.py` holds one frozen `CoachSignal` row per flat pack section (its coaching-question group, its flat position, its `PromptFeature` gate, its byte-stable drop + nested trim, its `COACH_*_ENABLED` kill switches with each switch's effect — drop/degrade/trim — and where it is applied, its read-time adapters, and either a kill switch or a recorded `ungated_reason`). `coach_context.py` derives `_SECTION_GROUP`/`_FLAT_ORDER`/`PACK_SECTIONS` from it; `context.py` derives its `ReadTimeSignal` objects from it, registering only the `compute` so the gate and the drop-effect kill switch are stated once (`gather` applies both, and the duplicate `if not settings.X` inside the memory and training-history builders is gone). Import-time checks fail loudly on a pack field with no declaration, a declaration for a field that does not exist, a signal unreachable through `from_sections` or a flat accessor, a kill switch naming a nonexistent setting, an adapter whose seam-applied switch the signal does not declare as a drop, and a signal stating neither a kill switch nor an ungated reason. `prompts.GROUPED_PACK_PROMPT_IDS` likewise stopped being hand-maintained: `PromptFeature.GROUPED_PACK` joined the manifest and the set derives via `ids_with` like every sibling.
The material distiller (`services/coach/material_distiller.py`, P4) is a separate structured-output-only ingestion path, not part of the exchange pipeline: `distill_material` runs one hardcoded `claude-haiku-4-5` FORCED-tool call (`AnthropicClient.generate_structured`, no free-form channel and no extended thinking) over an uploaded `UserMaterial`'s `raw_text`, coerces the tool output through the strict `DistilledMaterial` schema, and persists the corpus-`School`-shaped record (or `status=failed` on any off-shape/transport error); it runs in the background via `distill_material_job` and does not yet feed any exchange (the seam/pack/prompt are a later slice). This is the containment spine for the first untrusted-input surface (ADR 0017): structured-output-only + strict coercion + raw never entering a prompt.
ADR 0025 (M1-M5) replaced the durable-memory half of ADR 0008 — the deterministic belief loop (`beliefs.py`/`belief_store.py`/`CoachingContext`), the LLM `narrative` (`narrative_store.py`/`consolidation.py`/`CoachNarrative`), and the M10 derived-preference reranking (`preference.py`) — with the rewrite-from-source runner memory profile: `memory_store.py` is the `runner_memory` DB layer and `memory_update.py` (M2) the writer. Each pass `gather_memory_sources` bundles the runner's OWN check-in notes + chat statements (durable §1-§4 graduation requires >=2 distinct sources, re-derived from this pass's source set each time) plus a bounded recent-exchange-digest window (citable for the `lately` thread-state only — a coach digest can never graduate a durable line), and the writer rebuilds the WHOLE profile from that bundle via one hardcoded `claude-haiku-4-5` call, NEVER reading the stored profile, so the anti-echo guarantee is a property of input construction (CI-pinned). After each non-fallback report `service.py`'s `_fire_learning_loop` enqueues ONLY `update_memory_job` (the M8/A2c write-backs are gone), gated on a memory-aware prompt + `COACH_MEMORY_ENABLED`. Memory holds no behavioral verdict; whether the last advice worked and whether the runner is trending easier are re-derived deterministically at exchange time (`time_in_zones`/`recent_training`/`discount_signals`/M7's raw outcome), spoken fresh under the v13 non-nag discipline and never stored. The drop migration `2f8b6d3a1c90` removed the `coaching_context` and `coach_narratives` tables and `activities.beliefs_written_at`.
The offline eval harness (M5) under `app/services/coach/eval/` is the deterministic quality gate for the long-horizon coaching milestones: it scores each `CoachReport` independently from its stored `report` + `context_pack` against fourteen rubric assertions (led-with-headline, discounted-inflated-HR (which abstains when a confounder fired on a non-elevated drift, #176), no-medical-overreach reusing validator rule 5, advanced-not-parroted, abstained-on-thin-trend, framed-for-adherence the adherence-framing check, load-not-framed-as-intensity the #168 check that the cumulative `effort_score` load number is not narrated as an intensity verdict, coached-not-caveated the #171 check that when per-rep interval data is present the report coaches it rather than headlining a low detection-confidence caveat or advising the lap button on a recorded-laps session, voice-preserved-safety-surface the P1.1 check that a fired referral nudge is still relayed regardless of voice, corpus-preserved-safety-surface the P1.2 check that a fired referral nudge is still relayed regardless of the selected coaching school, user-materials-preserved-safety-surface the P4 check that a fired referral nudge is still relayed regardless of any uploaded material, memory-preserved-safety-surface the ADR 0025/M3 check that a fired referral nudge is still relayed regardless of the runner memory profile, coached-direction-not-nagged the ADR 0025/M3 check that the report renders no binary acted/ignored non-compliance verdict about the runner — the retired belief loop's symptom, and body-not-made-the-subject the #742 check that, when the runner's stated build was surfaced, the report advises on training that body rather than on changing it and never reaches for a population index (the edge validator rule 5 does not reach: "lose ten kilos" is neither a dose, a diagnosis verb, a medication directive, nor an asserted clinical condition)), aggregates a repeatable scorecard scoped to the current `(prompt_id, schema_version)`, and flags regressions across versions; driven by `backend/scripts/eval_coach_reports.py` (the `make eval` / `make eval-selftest` targets). The procedure is documented in `docs/testing/coach-report-eval.md`. The harness scores BOTH output shapes (A3): the rubric extractors branch over the `CoachReportContent | CoachMessageReport` union, the loader parses 2.x rows as `CoachMessageReport` and `make eval` defaults to whichever family the active prompt selects, the scorecard carries a `tail_degraded` counter, and `eval-selftest` validates a good + deliberately-bad fixture for each shape. Under A4 the harness scores the fuller turn only: opener-only rows (an `opener_message` with an empty `message`) are skipped as not-yet-complete and counted in a `skipped_opener_only` scorecard field, never scored.
The notifications layer is a port (`NotifierPort` in `app/services/notifications/port.py`) with `TelegramNotifier` (HTTPS Bot API via `httpx`), `InMemoryNotifier`, and `NoOpNotifier` (the `SMTPNotifier` email channel was removed, #595). `build_coach_notification` in the package `__init__.py` renders a `Notification` for the active channel, keeping the pipeline channel-agnostic; `build_receipt_notification` (#296) renders the deterministic receipt's `Notification` directly from plain inputs (the receipt has no `CoachReport`), carrying the fixed RPE/pain/done tap keyboard over Telegram; `telegram_template.py` renders the Telegram message (title + plaintext body + activity URL); it branches on the report shape via `notifications/_prose.py` to render the A3 prose `message` directly (Telegram truncates at a paragraph boundary under its 4096-char limit) instead of the structured takeaway/next-step lists. `callback_token.py` encodes/decodes the opaque <=64-byte tap tokens carried in `callback_data` (the I1b `rpe`/`pain` kinds plus the #296 value-less `done` control kind), and `TelegramNotifier` additionally exposes `answer_callback` (the tap toast) and `edit_message_reply_markup` (the tapped-button check mark).
The webhook/self-heal convergence is `app/jobs/process_new_activity.py` (ADR 0004, reshaped by A1/ADR 0011): ingest → analyze → block assignment, then under the two-stage prompt `_schedule_block_complete` (RQ-native `queue.enqueue_in` at +`BLOCK_GAP_SECONDS` — the grouping gap doubles as the debounce). `block_complete_job` no-ops unless its activity is still the block's last member (idempotency over cancellation; a newer member's check owns the block), the exchange is unopened, and the active prompt is two-stage (a check pending across a rollback flip is a logged no-op, AC6); it then runs the opener stage on the block's PRIMARY activity (`generate_opener` → `Exchange.opened_at` → conditionally `_schedule_fuller_turn` → notify via `Exchange.opener_sent_at`). `fuller_turn_job` runs stage two later (timer-fired or reply-fired), idempotent on `Exchange.fuller_sent_at`, and `maybe_enqueue_fuller_turn` fires it early (on the primary) from the check-in/chat reply paths of ANY block member when the exchange is open — `opened_at` set, `fuller_sent_at` null, within the reply window (ADR 0010). A late activity grouping into an open exchange joins the block (the pending fuller covers the larger event at fire time); into a closed one it starts a new block. The single-shot rollback path is the prior per-activity pipeline, still gated by `Activity.coach_notification_sent_at`. The per-event cadence dispatch — which of single-shot / opener-fuller / receipt fires on ingest, block-complete, reply, and "done" — is consolidated behind a swappable seam, the `app/jobs/cadence/` package (`PostActivityCadence` + `SingleShotCadence`/`OpenerFullerCadence`/`ReceiptCadence`, resolved at fire time by `get_active_cadence(settings)` so the config-flip rollback is preserved; #330/ADR 0019), one module per cadence since #696 so a cadence reads top-to-bottom in one place; the cadence-agnostic side effects it orchestrates (notify + sentinel, block/exchange resolution, deferred scheduling, the fuller turn) live in `app/jobs/exchange_ops.py`, and `process_new_activity.py` keeps the RQ entrypoints, the ingest orchestration, and the stable delegators other modules import.
`services/schedule/` (#830) is the schedule package — the product's first forward-facing surface after building only retrospective ones: `disciplines.py` maps a logged activity's type to the schedule's discipline vocabulary (routed through `activity_facts.is_run` so `run` means the same thing here as everywhere else, and `TrailRun`/`VirtualRun` land in `other` until #644 widens `is_run`); `placement.py` derives placement, the effective window, and session status purely from a session's stored `[window_start, window_end]` and today's date — nothing about placement is a column; `rules.py` is the closed five-kind spacing-rule vocabulary with one pure predicate each, checked by a backtracking constraint search (`find_assignment`/`check_rules`) that answers "does a legal arrangement exist" rather than linting a placement that mostly does not exist yet, sound because every predicate is monotone; `store.py` holds the owner-scoped reads/writes (every function takes a required `user_id`, and the two JSON columns on `TrainingPlan` are strict-coerced on the way out, off-shape rows skipped rather than raising); `norms.py` (a follow-up) is the one definition of the runner's typical RUNNING week (`running_norm_weekly_m`/`running_vs_norm`, built on the same `activity_facts` clamped per-day primitives), shared by `week.py`'s free-mode gauge and `draft.py`'s context — collapsing what had been `draft.py`'s own private copy; `week.py` builds the week read (planned or free — free mode is the same read with no active plan, not a second screen, measured against the runner's own norm); `horizon.py` builds the multi-week shape read (a week is `planned` only when it holds a real `PlannedSession`, `sketched` when only a `PlannedWeekShape` exists, both derived rather than stored); `draft.py` is the generation itself — assembles the drafting context, runs the metered `TurnKind.SCHEDULE` call, drives the rewrite/retry loop, and persists an accepted plan; `draft_contract.py` is the forced-tool schema (`record_training_plan`) and its strict `DraftedPlan` coercion; `plan_validator.py` is the deterministic coherence gate a draft must pass before `draft.py` will store it; `effort.py` is the runner's-own-history load pricer (`build_load_model`/`estimate_effort`) the model is never asked to estimate itself; `completion.py` (#830) is the one write for marking a session done (`complete_planned_session`, the `write_checkin` precedent) reached from three routes — the ingest pipeline's auto-match (`complete_from_activity`/`find_matching_session`, conservative on discipline/window/`MIN_COMPLETION_FRACTION` and idempotent on `completed_activity_id`), a manual tap, and the coach's confirmed `complete_session` proposed action — plus `dismiss_planned_session` (a suggestion only) and `clear_completions_for_activity` (the Strava-delete path, `AUTO` completions only); `find_matching_session` doubles as the source `_extract_planned_workout` reads in the load phase of `analyze`, so the same match answers both "is this session done" and "what was this run planned to be." `coach_view.py` (#830 final slice) is the newest module: `build_schedule_context` reads the runner's active plan plus this activity's matched session (via `completion.find_matching_session`) into a `right_now.schedule` coach-pack section scoped to the WEEK, never the twelve-week horizon — what THIS activity was planned to be (`_target` renders the prescription, e.g. "6 x 800 m off 90 s", never `effort_score`, the North Star's hard case again), the committed sessions still to come this week (`_when`), the spacing rules in play, and two counts (`committed_this_week`/`done_this_week`); it states no adherence label, percentage, or per-session hit/miss flag, since handing a model a plan and a result invites exactly the compliance verdict ADR 0025 was built to remove, and returns `None` (byte-stable drop) for a runner with no plan. The package computes no training total of its own: actuals and windows come from `activity_facts`, the week boundary from `weeks.py`, and "typical" from `coach/volume.py`'s existing `build_training_volume` (all-activity) and its own `norms.py` (running-only), so the schedule cannot become a second opinion about a week the Trends page has already answered. The section is declared as one appended `CoachSignal` row (group `right_now`, gate `PromptFeature.SCHEDULE`, droppable, one read-time adapter, its own `COACH_SCHEDULE_ENABLED` kill switch applied in `read_time_signals.gather` — appended rather than inserted, because the flat declaration order IS the pack's serialization order) and rides `coach_message_lean_grouped_v9` (grouped_v8 plus `PromptFeature.SCHEDULE` and one added fuller-prose clause), absent until the runner has an active plan; `grouped_v9` went live in production on 2026-08-12 (owner runbook `docs/deployment/coach-schedule-v9-cutover.md`), so the coach now reads the plan for any runner who has one. #830's completion slice closes the loop the other way: a session gets marked done through `completion.py`, not yet through free-form conversational plan-editing (the coach can only confirm the one narrow `complete_session` proposed action, never rewrite a session or a rule).
The frontend is a Next.js 14 App Router project; pages live under `frontend/app/`, reusable UI under `frontend/components/`, and the typed API client and shared types under `frontend/lib/`.
Data flow: Strava API → strava_ingestion → Activity/ActivityStream rows → analysis pipeline → DerivedMetric → coach service → CoachReport → either (a) frontend via `/api/activities/{id}/coach-report`, or (b) notifications via the pipeline job's Telegram send.

## Testing Overview

Backend tests run via `python -m pytest`; the global baseline command is `make backend-test`, which excludes tests marked `integration`.
The test session deliberately opts OUT of `backend/.env` (#752): `tests/conftest.py` sets `RUNNING_COACH_SKIP_DOTENV` (and a dummy `DATABASE_URL`) before importing the app, and `Settings.model_config` then drops `env_file`, so a local run resolves exactly the code defaults CI resolves — CI has no `.env` and sets only that same dummy. Before this, a developer `.env` carrying prod-parity coach configuration made `make backend-test` report 99 failures locally against 0 in CI, since a large family of tests pins byte-stable behaviour against the DEFAULTS. `tests/test_settings_isolation.py` guards both halves (no env file in play; every `COACH_*` setting equal to its declared default, matched by prefix so the growing kill-switch family needs no list maintenance). The opt-out covers the env FILE only — a variable exported in the developer's shell still wins, which is why the older per-family autouse fixtures (`_isolate_notification_channels`, `_disable_clerk_auth`) remain.
Backend smoke is a single file (`backend/tests/test_smoke.py`) covering a FastAPI health-check readiness path.

## Real-Data Verification

There is no Strava OAuth application for dev or local, so the connect-then-sync path cannot bootstrap data outside production; real-data verification therefore uses one of the two paths below, both documented in `docs/testing/local-seed.md`.
Path 1 (deployed): the production Vercel app (`https://ai-running-coach-eta.vercel.app/`) is publicly reachable and renders real synced data because the frontend injects the backend's HTTP Basic credentials server-side, so browser automation against it verifies any UI or read-path change with no local setup; per-branch preview deployments sit behind Vercel SSO and are not reachable by unauthenticated automation, so pre-merge UI verification uses Path 2.
Preview deployments are not isolated environments: they point at the same single production backend and Postgres/Redis as production, so any write triggered on a preview (sync, destructive migration, delete) mutates production data.
Path 2 (local): `make seed-local` runs `backend/scripts/seed_from_prod.py`, which resets the local schema to the branch's migration head and copies a production snapshot (users, profile, Strava account, baselines, coaching relationship/context/narrative, activities, blocks, exchanges, streams, derived metrics, coach reports, coach threads, chat, check-ins; a table the source does not have yet arrives empty (a branch adding a table still seeds from un-migrated prod); activities are inserted with `block_id` nulled and backfilled after blocks land, because the activities/blocks FKs are circular) so the analyze -> coach -> frontend chain runs offline against real data; `SEED_ARGS="--activities N"` bounds the snapshot.
The seed redacts Strava tokens by default so local cannot call Strava and cannot rotate the production refresh token, which means the home page "Sync Now" action fails on a seeded local DB; `SEED_ARGS="--with-live-tokens"` is the opt-in for exercising a real sync and shares the production token.
`seed_from_prod.py` reads the source URL from `SEED_SOURCE_URL` (the `make` target injects Railway's `DATABASE_PUBLIC_URL` via the project token at `~/.railway_token`), only ever reads from the source, and refuses any target URL that is not `localhost`/`127.0.0.1`.
Local verification runs the backend via `uvicorn app.main:app --port 8000` and the frontend via `npm run dev` (port 3000) against the docker-compose Postgres/Redis; `BasicAuthMiddleware` is a no-op locally when `BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD` are unset, so local API calls need no credentials.
Because Phase-2 Clerk auth (ADR 0022) otherwise requires a verified session on the backend and a sign-in on the frontend (which an agent cannot complete), the dev-only ungated browser-verification mode (#488) is the supported Path 2 browser path: `make verify-local` runs the backend with `LOCAL_NO_AUTH=true` (forces the single-seeded-user Clerk degrade even with `CLERK_JWKS_URL` set) and the frontend with `NEXT_PUBLIC_LOCAL_NO_AUTH=true` (Clerk gate off). Both fail closed in production — `LOCAL_NO_AUTH` is ignored when `APP_ENV=production` (the backend stays the enforcer, unconfigured Clerk still 503s) and `NEXT_PUBLIC_LOCAL_NO_AUTH` is honoured only in a non-production `next dev` build — so it is no prod bypass, and the normal Clerk-on local flow is unchanged. The target does not start the rq worker (read-path/UI verification); run one separately to exercise background jobs. The two deployed-only handshakes that cannot be bootstrapped locally (Strava OAuth `state`, Telegram `/start` bind + tap auth) have a manual deployed runbook at `docs/testing/deployed-handshake-verification.md` (#534).
