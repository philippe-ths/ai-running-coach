> Domain vocabulary lives in `CONTEXT.md`. This file describes the current implementation; the glossary describes the language.

## Product Summary

Running Coach is a single-user MVP that connects to Strava, ingests running activities, computes training signals, and produces opinionated post-run analysis.
The intended user is an individual runner connected to their own Strava account; the app runs either locally via docker compose or as a deployed single-user instance on Railway (backend, Postgres, Redis) and Vercel (frontend). Phase 2 introduces multi-user signup per ADR 0005.
The core flow is: connect Strava → sync activities → deep-process a run → view derived metrics and an LLM-generated coach report on the activity page.

## Domain Concepts

A `User` owns a `UserProfile` (goal, experience, weekly volume, max HR, races, injuries) and a linked `StravaAccount` (OAuth tokens, athlete id).
An `Activity` is a single Strava activity record owned by a `User`, identified by `strava_activity_id`.
An `ActivityStream` holds per-sample time-series data (HR, pace, cadence, power) attached to an `Activity`.
A `DerivedMetric` row attaches one set of computed signals to one `Activity` (activity class, effort score, pace variability, HR drift, time-in-zones, stops, efficiency, intervals, flags, confidence, risk, discount signals, consolidated stream view). The consolidated stream view (A2a) is a small downsampled aligned HR/pace/grade/cadence snapshot, a processed artifact derived during analysis and pulled on demand, never a source of truth.
A `Block` (A1, ADR 0011) groups a user's temporally-contiguous activities into one training event by deterministic time-gap clustering (an activity strictly under `BLOCK_GAP_SECONDS` from an existing block joins it, symmetric so out-of-order sync converges; a block whose exchange is closed never absorbs — the late activity starts a new block), carrying `start_date`/`end_date`, a `primary_activity_id` (the run, else the longest member; frozen once the block's exchange has opened so the report anchor never moves; recomputed by explicit corrections), and a `user_corrected` audit bit; `activities.block_id` is the membership FK, assignment runs at ingestion on every ingest path, and the A1 migration backfilled every analysed non-deleted historical activity into a block-of-one.
An `Exchange` (A1) is the first-class two-stage lifecycle row for one `Block` (`block_id` UNIQUE, created with the block): `opened_at` marks opener generation (anchors the reply window, independent of delivery so a NoOp local notifier still works), `opener_sent_at`/`fuller_sent_at` are the per-stage at-most-once notification sentinels relocated from `Activity` (whose `opener_notification_sent_at`/`coach_notification_sent_at` stop being written under the two-stage path but are retained — their removal is a separate approved delete; the single-shot rollback path still dedups on the Activity sentinel because per-activity dedup needs a per-activity store), and `fuller_sent_at` set means the exchange is CLOSED; backfilled exchanges read as closed. `coach_reports` is untouched: still the versioned generation artifact keyed `(activity_id, prompt_id, schema_version)` on the block's primary activity.
A `CoachingRelationship` (A1) is the thin one-row-per-user durable anchor of the coaching relationship (id, unique `user_id`, `created_at`), auto-created on first profile read like `UserProfile`; P1's voice/stance dials extend this row rather than create it.
A `CheckIn` captures subjective post-run input from the user against an `Activity`.
A `CoachReport` is the cached LLM analysis for an `Activity`, keyed by `(activity_id, prompt_id, schema_version)` so a prompt/schema change retains prior-version reports instead of overwriting them; its `report` JSON holds one of two shapes by schema-version family (ADR 0009): the legacy structured `CoachReportContent` (schema 1.2) or the A3 prose `CoachMessageReport` (schema 2.0, a human prose `message` plus a thin structured tail). Under the A4 two-stage Exchange (ADR 0010) the schema-2.0 `CoachMessageReport` also carries an `opener_message` (the stage-one prose) and a `schedule_fuller_turn` bit; one evolving row holds both stages (the opener writes `opener_message` with `message` empty, the fuller turn fills `message` in place preserving the opener). `CoachChatMessage` rows form a follow-up conversation against that activity.
A `RunnerBaseline` (one row per user) stores rolling baselines used for comparison and drift detection: per-user scalar typicals plus a `bucketed_trends` JSON map of EF and HR-drift trends bucketed by `effort|terrain|temperature-band`, computed by `services/analysis/baseline.py` and recomputed at the end of `analyze` over a rolling `BASELINE_COMPARISON_WINDOW_DAYS` (182d / ~26wk) window anchored on the runner's most recent activity (so per-activity recompute cost stays flat as history grows, #167); a bucket abstains until it has `MIN_SAMPLES_FOR_TREND` (4) like-for-like samples.
A `CoachingContext` row is one durable, user-scoped belief (M8): a deterministically-derived, write-gated, TTL-tiered fact the coaching relationship has learned (a confirmed HR confound, an adherence tendency), identity `(user_id, kind, key)`, carrying `value`/`confidence`/`observation_count`/`status`/`last_reinforced_at`; written after each non-fallback report and retrieved (active, non-decayed, observation_count >= 2) into later context packs as prior context that never overrides the run's re-derived `DerivedMetric`.
A `CoachNarrative` (one row per user, A2c) is the LLM-written, voice-only half of durable memory: the bounded relationship story (plus provenance — model used, source-report count, grounded-through date), re-written from the deterministic facts + recent exchange digests by the background `Consolidation` job. It is authoritative for voice but never for fact: it can never be cited as evidence (validator rule 6) and never overrides the run's re-derived `DerivedMetric` (prompt rule 24). Distinct from `CoachingContext` (deterministic, auditable facts) and `RunnerBaseline` (numeric norms).

## Scope

The backend exposes JSON endpoints under `/api` for health, Strava OAuth, profile CRUD, activity listing/detail, sync, deep processing, historical stream backfill, intent labelling, check-ins, trends, training load (`GET /api/trends/load`, #209: chronological weekly load scores with a trailing-4-week optimal band, day-of-week breakdown, and per-activity contributions), coach report, coach chat, and block split/merge correction (A1: `POST /api/blocks/{id}/split` at a member activity and `POST /api/blocks/{id}/merge` with an adjacent block; corrections set `user_corrected`, recompute bounds/primary, inherit the exchange stage sentinels so nothing ever re-fires, and there is no UI surface until I3).
Strava ingestion supports both manual sync (`POST /api/sync`) and incoming webhooks (`/api/webhooks/strava`); webhook `aspect_type=create` events enqueue `process_new_activity_job` (ingest → analyze → assign block; under the two-stage prompt `coach_message_v2` it then schedules `block_complete_job` at +`BLOCK_GAP_SECONDS` instead of generating inline — see the A1 paragraph below — while single-shot prompts run the per-activity report → notify immediately), `update` events enqueue `sync_activity_job` (re-ingest only), and `delete` events soft-delete the activity row.
Both pipeline enqueue points (webhook create and polling) attach the bounded `PIPELINE_RETRY` policy (3 attempts at 60/300/900s, defined in `app/jobs/process_new_activity.py`), so a worker crash mid-pipeline re-runs the idempotent job instead of permanently stranding an ingested-but-unprocessed activity that polling would treat as already known.
`HTTPStravaAdapter.list_recent_activities` paginates `/athlete/activities` until a short page, capped at `_MAX_PAGES` (40), so a window wider than one page no longer silently truncates to the first 50 activities.
`POST /api/sync` takes `since_days` (default 30); windows up to 30 days fetch streams (full deep processing), while larger windows import activity summaries only (`ingest_recent_activities(fetch_streams=False)`) as a rate-limit-safe historical backfill since each activity's streams cost a separate Strava call.
`POST /api/activities/backfill-streams` enqueues `backfill_streams_job`, a manually-triggered self-pacing job that fills the stream-derived-analysis gap left by summary-only imports: each batch fetches streams and re-runs analysis for up to `BACKFILL_BATCH_SIZE` activities that still lack them, marks each via `Activity.streams_backfilled_at` (so it is resumable and attempted exactly once), schedules its successor via `rq-scheduler` `enqueue_in` while work remains, and never notifies.
Incoming webhook events are authenticated before any side effect by `_event_is_authentic` in `app/api/webhooks.py`: `owner_id` must match a connected `StravaAccount`, and `subscription_id` must match `STRAVA_WEBHOOK_SUBSCRIPTION_ID` when that setting is non-zero, otherwise the request is rejected with 403.
Inbound Telegram button taps POST to `/api/webhooks/telegram`, authenticated before any side effect by the `X-Telegram-Bot-Api-Secret-Token` header matching `TELEGRAM_WEBHOOK_SECRET` (fails closed in production when unset) plus a chat-id match against `TELEGRAM_CHAT_ID`.
An authentic RPE/pain tap writes the same `CheckIn` the in-app endpoint writes (both go through `write_checkin` in `services/checkins.py`), re-analyzes the activity, fires the open exchange's fuller turn early, check-marks the tapped button on the opener's inline keyboard (a re-tap moves the mark; only the keyboard is edited, never the message text), and answers the callback with an ephemeral toast.
A polling fallback (`poll_for_new_activities_job`) discovers activities Strava webhook missed and converges on the same pipeline; it runs every `POLLING_INTERVAL_SECONDS` via an `rq-scheduler` process.
Deep processing classifies the activity, computes metrics from streams (smoothing, splits, intervals, stops, efficiency, risk), and runs workout matching against any planned workout.
The coach pipeline builds a context pack, calls Anthropic, validates the response against a Pydantic schema, then runs a deterministic policy validator before storing the report; LLM/parse failures persist a fallback `CoachReport` with `is_fallback=True`.
The coach output has two shapes keyed by prompt family (ADR 0009, A3): the legacy structured `CoachReportContent` (schema 1.2, `coach_report_*` prompts) and the A3 prose `CoachMessageReport` (schema 2.0, `coach_message_*` prompts) — a human prose `message` written before any structure (adaptive thinking → message → one strict-tool tail carrying `headline`/`next_steps`/`risks`/`questions` with typed `TappableOption`s), stored in the same `coach_reports.report` JSON column (no migration); `service.active_schema_version(prompt_id)` resolves the cache identity from the prompt-id prefix (`SCHEMA_VERSION_BY_FAMILY`), so cutover and rollback are each a pure `COACH_PROMPT_ID` config flip. `get_or_generate_coach_report` dispatches on family to `_generate_structured` or `_generate_message` (the A3 single call `llm.generate_coach_message` + the `output_contract.py` parse/merge); the prose path degrades-not-withholds (a real message survives a missing/unusable tail as `tail_degraded=True` with empty `next_steps`, the loop then abstains) and a medical-overreach violation surviving the policy retry forces `is_fallback=True` (the one A3 strengthening, since prose renders verbatim). The tail's `next_steps` land at the same JSON key/shape `retrieval.fetch_prior_commitments` reads, so the M4-M10 loop survives the cutover by construction; `digest.py` projects the message's first sentence as the digest lead. The config default stays `coach_report_v10`; production runs `coach_message_v2`.
The context pack carries a `block` section (A1) ONLY for a multi-member block: the chronological member list (type/duration/distance, primary marked) plus combined totals, built by `_build_block_context` in `context.py` so the coach can speak about the morning as a whole; a block-of-one emits no key at all and its pack is byte-stable against the pre-A1 shape (AC8, pinned by test — `to_serializable_dict` drops the null field). Novelty, digests, baselines, and the M4-M10 learning loop stay activity-level through the primary activity.
The context pack carries a `longitudinal` section (M4): a token-bounded digest of the runner's last 1-2 non-fallback reports (date, headline, `lead_argument`, recommended `next_steps` only, never the full body) plus the matching `RunnerBaseline` bucket trend for this run's `effort|terrain|temp-band` context (omitted while that bucket still abstains), so the report advances the prior narrative instead of restating it.
The context pack also carries a `perceived_effort` section (M6, computed by `services/coach/perceived_effort.py`): the gap between the runner's subjective `CheckIn.rpe` and the HR-derived `effort` axis (a signed 1-5-band divergence; divergence is computed against the intensity axis, not the cumulative TRIMP-like `effort_score`, which is carried raw), a `recommended_weighting` that favours RPE over HR when an N4 `discount_signals` confounder fired (RPE survives HR distortion), and a `pain_trend` over recent check-ins (abstains under `MIN_PAIN_SAMPLES`, never a diagnosis); it degrades to nulls when no check-in exists.
The context pack also carries an `adherence` section (M7, the "gets better over time" loop, pure logic in `services/coach/adherence.py`, gathered by `_build_adherence_context` in `context.py`): for each `next_step` in the most recent prior non-fallback report, a `NextStepOutcome` labelling the runner's subsequent comparable activity `acted_on`/`ignored`/`contradicted` (or `disputed` when overridden), re-derived on demand from the already-stored `Activity`/`DerivedMetric` rows (no durable store; M8 owns the gated belief store). A step abstains (no outcome) unless it maps to a recognised theme (`easy_discipline`, `add_quality`, `add_long_run`), survives a negation/caution guard (so "hold off on adding intensity" is never read as "add intensity"), has a comparable non-low-confidence run to judge against, and (for the window themes) the runner has had `_MIN_OPPORTUNITY_RUNS` comparable runs before a miss is called `ignored`. Easy-discipline excludes races, detected interval sessions, and declared workouts from comparability, and only asserts the strong `contradicted` when the run's `user_intent` was explicitly easy (an unlabelled hard run is softened to `ignored`, since this single-user dataset carries no intent labels and a hard run may have been deliberate). An explicit `CheckIn.notes`/`CoachChatMessage` pushback on the prior report flips the implicit label to `disputed`, which the prompt treats as settled (says nothing), so a false-positive pushback only suppresses a note. It degrades to empty (the coach then says nothing about adherence) when there is no prior report.
The context pack also carries a `believed_facts` section (M8, the belief-state write-back loop, pure logic in `services/coach/beliefs.py`, DB layer in `services/coach/belief_store.py`): the runner-model accumulated from prior reports. After each non-fallback report, `write_back_beliefs` deterministically extracts belief deltas (a confirmed `hr_confound` from `discount_signals`, `adherence_pattern` outcomes from M7) and creates or reinforces rows in the durable user-scoped `CoachingContext` table; `build_believed_facts` retrieves the active, non-decayed, quality-cleared beliefs (observation_count >= 2) into the pack with `confidence` + `last_seen_days_ago` tags. Beliefs decay by a TTL tier (`hr_confound` 120d, `adherence_pattern` 90d) measured from last reinforcement, an opposing adherence observation resolves the belief's direction in place (acted/total counts), and a belief never overrides this run's re-derived `DerivedMetric` (prompt-enforced). Belief deltas are deterministic, never LLM-generated, so they stay auditable.
The context pack also carries a `calibration` section (M9, pure logic in `services/coach/calibration.py`, gathered by `_build_calibration_context` in `context.py`): `hr_drift` reads this run's HR drift against the runner's own typical drift for the matching `effort|terrain|temp-band` bucket (computed at read time from prior comparable runs, since the RunnerBaseline is recomputed after the pipeline), marking `calibrated` true with an `above`/`below`/`in_line` comparison once `MIN_SAMPLES_FOR_CALIBRATION` (4) comparable runs exist, else falling back to the labeled population ~5% drift heuristic; and `referral`, a non-diagnostic clinician nudge fired only on computable red-flag patterns (the `illness_or_extreme_fatigue` flag, or sustained notable pain across recent check-ins), templated to pass the medical-scope validator and abstaining otherwise. Neither overrides the re-derived `DerivedMetric`.
The context pack also carries a `preference_profile` section (M10, the capstone, pure logic in `services/coach/preference.py`, gathered by `_build_preference_profile` in `context.py`): the per-runner signal of which advice themes the runner acts on / ignores / is mixed on, derived from the accumulated M8 adherence_pattern beliefs (`build_preference_profile` ranks themes with `MIN_TOTAL_FOR_TENDENCY` (3) observations as `acts_on` >=0.7, `ignores` <=0.3, else `mixed`). It is a no-fine-tune, preference-conditioned framing signal (T-POP style): the coach reranks/frames its next_steps toward what the runner acts on, never overriding the re-derived `DerivedMetric` or fabricating advice. It is already explicit-feedback-aware (M8 never reinforces a belief from a disputed outcome). The M5 eval gains a sixth assertion `framed_for_adherence` (conservative: fails only when next_steps are confined to ignored themes when a decisive profile exists).
The active prompt is `coach_report_v10` (default): it adds the "advance, do not restate" discipline (rule 16, M4), the perceived-effort RPE-weighting discipline (rule 17, M6), the adherence "advise, do not nag" discipline (rule 18, M7), the believed-facts "apply, hedge by tags, never override today's data" discipline (rule 19, M8), the calibrated-correction + non-diagnostic-referral discipline (rule 20, M9), the preference "frame toward what the runner acts on" discipline (rule 21, M10), the load-vs-intensity discipline (rule 22, #168: `effort_score` is cumulative TRIMP-like training load that grows with duration, never an intensity verdict; intensity comes from the HR-derived `effort` axis / RPE), the coach-the-available-data discipline (rule 23, #171: when per-rep `interval_structure` data is present, lead with that analysis; a low interval `detection_confidence` is a bounded caveat about exact structure, never the headline/thesis or grounds to call the session uncaptured, and never a reason to advise the lap button when `source="recorded_laps"`), and the relationship-narrative discipline (rule 24, A2c: the durable-memory `narrative` section is voice only — it sets tone and continuity, is never cited as fact, never derives a number, and never overrides this run's re-derived data; hedge a thin/stale story by its `source_report_count`/`last_updated_days_ago` tags), while retaining byte-stable `coach_report_v1`..`coach_report_v9` for prior cached reports. Output schema is unchanged across v1-v10 (SCHEMA_VERSION stays 1.2); only `prompt_id` advances, which the M0 versioned cache uses to regenerate and retain history. Unlike A2b (behaviour-preserving), v10's emitted pack legitimately carries a new `narrative` section, so v10 reports regenerate.
`coach_message_v1` (A3, schema 2.0) is a fresh prose-first prompt, not derived from the `coach_report_v*` chain: it carries every substantive grounding/safety/coaching discipline of rules 2-24 rewritten for prose plus the three-movement output protocol (reason privately → write the prose `message` → call `record_coach_tail` once, restating only what the message said), and is selected by setting `COACH_PROMPT_ID=coach_message_v1` (cutover is a config flip, not yet the default).
The A4 two-stage Exchange (ADR 0010, `coach_message_v2`, schema 2.0 unchanged) turns a finished activity into an immediate lightweight **opener** then a conditional deep **fuller turn**, gated by `Salience`. One prompt, two modes, selected by the caller (not by prompt id — both stages share the `coach_message_v2` cache identity and one evolving `coach_reports` row): `build_system_prompt(prompt_id, mode="opener"|"fuller")` returns the lean opener prompt (a brief reaction + RPE/pain prompts + a `schedule_fuller_turn` judgment, no playbook) or the fuller prompt (`coach_message_v1` verbatim + a continuity rule). `service.generate_opener` writes an opener-state row (the opener prose in `CoachMessageReport.opener_message`, `message` empty, no digest, NO learning-loop write-back) and returns the schedule decision (the opener LLM's `schedule_fuller_turn` OR the deterministic safety override). `service.generate_fuller` reads the opener prose + any reply as `continuity`, runs the fuller call, fills the SAME row in place preserving `opener_message`, and fires the M4-M10 write-back + `Consolidation` on completion (non-fallback only); it is also the on-demand path (`get_or_generate_coach_report` delegates to it under `coach_message_v2`). Salience is hybrid: a deterministic **novelty** signal (`services/analysis/novelty.py`, first-of-its-kind axes vs the runner's analysed history, abstains under `MIN_HISTORY_FOR_NOVELTY` 3) and a deterministic **safety override** (`services/coach/salience.py`, reusing `calibration.assess_referral`'s red-flag predicate to force a fuller turn on a red-flag run) ride a new `salience` pack section; a `continuity` pack section carries the opener prose + chat reply for the fuller turn. The opener's prose+tail is policed by `validate_message_policy` exactly as the fuller turn (`_extract_message_text` includes `opener_message`). The two-stage cadence is gated on the active prompt being `coach_message_v2`, so flipping `COACH_PROMPT_ID` back to `coach_message_v1`/`coach_report_v10` serves the prior single-shot path with zero code change; `fuller_turn_job`/`process_fuller_turn` and `generate_fuller` carry the same gate, so a fuller already scheduled before a rollback fires as a logged no-op instead of leaking a wrong-prompt generation. Two-stage timing: `EXCHANGE_STAGE2_DELAY_SECONDS` (3h fuller-turn timer fallback) + `EXCHANGE_REPLY_WINDOW_SECONDS` (24h reply window); the config default stays `coach_report_v10` while production runs `coach_message_v2` on Railway.
Coach-report email delivery is gated by `SMTP_HOST` and `NOTIFY_TO`; with both unset the notifier is a no-op. Each Exchange stage sends its own notification (A4): the opener via `Activity.opener_notification_sent_at`, the fuller turn via `Activity.coach_notification_sent_at` (also the fuller job's idempotency guard); both are per-stage at-most-once dedup sentinels that a `force=true` regeneration never resets. `build_coach_notification(..., stage="opener"|"fuller")` renders the opener prose + a "let me know how it felt" line, or the fuller message, via `_prose.py`; only the opener's Telegram notification carries an inline keyboard of tappable RPE/pain buttons (`_opener_actions` building opaque `callback_token.py` tokens from the report's `TappableOption`s), the fuller carries none.
The frontend renders an activity list on the home page (each item carrying its classification headline, #136), a per-activity detail page with charts and panels (the stream charts support synced touch/drag scrubbing with a per-chart value readout, #207; a Laps panel renders the runner's recorded Strava laps — projected at read time from `raw_summary` into `ActivityDetailRead.laps` by `services/laps.py`, hidden when fewer than two recorded laps — #208), a profile page, a trends page with filters and chart views, and a training-load page (`/load`, #209). The UI has light/dark/system theming (#175): `next-themes` toggles the `dark` class, Tailwind `darkMode: 'class'`, a `ThemeToggle` in the NavBar, choice persisted in localStorage.
Planned-workout capture is not yet implemented; `_extract_planned_workout` in `services/analysis/_orchestrator.py` returns `None` as a placeholder.
There is no multi-user auth layer; the backend assumes a single local user and auto-creates one on first profile read.
Railway runs the backend as three services off one image (`web` FastAPI, `worker` RQ jobs, `scheduler` rqscheduler) plus managed Postgres and Redis; Vercel hosts the Next.js frontend.
The Vercel frontend reaches the backend over HTTP: server components call `BACKEND_URL` directly and the catch-all route handler `frontend/app/api/[...path]/route.ts` proxies client-side `/api/*` calls, both injecting HTTP Basic credentials server-side so the browser never sees them.
The backend gates all routes with `BasicAuthMiddleware`, exempting `/api/health`, `/api/webhooks`, and `/api/auth/strava/callback`; this Phase 1 layer is replaced by ADR 0005 magic-link sessions in Phase 2.
Build and deploy config lives on the platforms rather than in an in-repo deploy manifest; the repo's only committed automation is the CI workflow under `.github/workflows/`.
Locally `docker compose` provides only Postgres and Redis, while the host runs `uvicorn`, `rq worker --with-scheduler`, an optional `rqscheduler`, and `next dev`.
The full production and local-dev topology, the connection seam, and per-service env var ownership are documented in `docs/deployment/topology.md`.

## Important Constraints

Settings come from `backend/.env` via `pydantic-settings`; `DATABASE_URL` is required and the app will not boot without it.
Anthropic access requires `ANTHROPIC_API_KEY`; the coach model id and prompt id are configured via `COACH_MODEL_ID` and `COACH_PROMPT_ID` (default `coach_report_v10`). Flipping `COACH_PROMPT_ID` to `coach_message_v2` activates the A4 two-stage Exchange; any other (single-shot) id serves the prior path with zero code change. The A2c Consolidation job's model is `claude-haiku-4-5`, hardcoded by design (no config knob): it is a summarise-from-structured-facts task.
The A4 two-stage Exchange cadence is configured via `EXCHANGE_STAGE2_DELAY_SECONDS` (default 10800 / 3h, the fuller-turn timer fallback fired via `rq-scheduler` `enqueue_in`) and `EXCHANGE_REPLY_WINDOW_SECONDS` (default 86400 / 24h, how long after the opener a reply still triggers the fuller turn early); both are inert under a single-shot prompt.
`BLOCK_GAP_SECONDS` (A1, default 1800 / 30min) is both the block grouping threshold and the block-complete debounce that gates the opener, so a solo run's opener arrives ~30 minutes after processing rather than instantly (a deliberate ADR 0011 trade); block ASSIGNMENT runs under every prompt (the data model is always on), while the block-complete opener trigger is two-stage-only.
Coach-report notifications pick a channel by config (`_active_channel` in `app/services/notifications/__init__.py`): Telegram when `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` are both set, else email when `SMTP_HOST` + `NOTIFY_TO` are both set, else a no-op. Telegram is the deployed channel because Railway blocks outbound SMTP from the worker (#127); the Bot API runs over HTTPS. Email transport is configured via `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_USE_STARTTLS`.
The Telegram vars must be set on BOTH Railway app services: the worker sends outbound notifications, while the web service authenticates inbound callbacks and edits the tapped keyboard; `TELEGRAM_WEBHOOK_SECRET` is needed on web only.
The polling fallback interval is `POLLING_INTERVAL_SECONDS` (default 120s, ~720 Strava calls/day per account, well under Strava's 1000/day limit).
The polling lookback window is `POLLING_LOOKBACK_SECONDS` (default 604800s / 7 days); each poll asks Strava for activities within this window, so an ingestion outage shorter than the window self-heals while a longer gap needs a manual `POST /api/sync` backfill. For a single recreational runner the window stays within one page, so it does not raise the steady-state call budget.
The historical stream backfill is paced by `BACKFILL_BATCH_SIZE` (default 20, activities per batch) and `BACKFILL_BATCH_PAUSE_SECONDS` (default 300, delay before the next batch); the default 20 stream calls per 5 minutes plus polling stays under Strava's 100-requests/15-min ceiling, and because the backfill is one-time its daily cost is just the backlog size and converges to zero.
CORS origins are configured via `CORS_ALLOWED_ORIGINS` (comma-separated, default `http://localhost:3000,http://localhost:8000`), parsed by `Settings.cors_allowed_origins_list` and applied in `app/main.py`.
Error tracking is logs-only by default; Sentry capture is opt-in, requiring the `observability` extra (`sentry-sdk[fastapi]`) installed and `SENTRY_DSN` set, otherwise `init_sentry` in `app/core/observability.py` is a no-op.
The deterministic policy validator in `services/coach/validator.py` has six rules: it rejects LLM output that misses questions for a null check-in, references uncalibrated HR zones, cites a risk flag not in the flags array, claims specific interval execution counts (e.g. "8x400m", "executed 8") under low detection confidence, (the medical-scope rule) gives dose advice, uses diagnosis verbs, issues directive medication advice, or asserts a clinical condition about the runner (while still permitting interpretive metric correction and a non-diagnostic referral nudge), and (the A2c narrative-is-not-evidence rule) cites a `narrative.*` field path as report evidence — the durable-memory narrative is voice only and can never ground a factual claim (deliberately narrow: it matches only the narrative section, so it never forces a false-positive fallback); per `ai-workflow.md` this gate must not be bypassed. The six rule bodies are shared `check_*` functions over primitives (a text surface, structured flags/questions, evidence paths, pack facts), assembled by `validate_policy` from the structured report and by `validate_message_policy` (A3) from the prose `message` + tail, so both output shapes are policed by one identical rule set; the message entry point polices the full prose plus every tail text field (including tappable-option labels), and the service forces `is_fallback=True` when a medical-overreach violation survives the retry on the prose path.
When data confidence is low, downstream analysis is expected to default to conservative output (documented intent in `README.md`).
Postgres is exposed on host port `5433` (mapped from container `5432`); Redis on `6379`; backend on `8000`; frontend on `3000`.
Backend test baseline excludes tests marked `integration` (pytest marker registered in `pyproject.toml`).

## Architecture Summary

The backend is a FastAPI app (`app/main.py`) wiring routers from `app/api/*` under the `/api` prefix.
Persistence uses SQLAlchemy 2.x ORM with a Postgres database; schema migrations live under `backend/alembic/versions/`.
Background work runs via Redis-backed RQ; jobs are defined in `app/jobs/` and the worker entrypoint is `python -m app.worker`, which runs `worker.work(with_scheduler=True)` because RQ parks interval retries in the ScheduledJobRegistry that only a worker-embedded scheduler thread drains (locally `rq worker --with-scheduler`). A separate `rqscheduler` process registers and fires the recurring polling job; bootstrap it once via `python -m app.jobs.scheduler`.
The Strava integration is a port (`StravaPort` in `app/services/strava_ingestion/port.py`) with `HTTPStravaAdapter` and `InMemoryStravaAdapter`; the ingestion module (`app/services/strava_ingestion/ingestion.py`) owns persistence and orchestration on top of that port (ADR 0002, ADR 0003).
Analysis is a pipeline of pure-ish functions in `app/services/analysis/` (smoothing, metrics, classifier, splits, intervals, stops, flags, risk, discount signals, workout matching) composed by `_orchestrator.py`; the public surface is `analyze` and `analyze_with_streams`. The interval-structure stage (`intervals.py`) has two sources behind one `interval_structure` contract: `detect_intervals_from_laps` reads the runner's recorded Strava laps from `raw_summary` (their own lap-button marks) as the authoritative segmentation and takes precedence when the laps show a clear bimodal work/rest pattern, tagging the structure `source="recorded_laps"`; `detect_intervals` (the velocity-stream smoothing + bimodal heuristic) is the fallback when no usable laps are present (#170). Lap-sourced structure skips the stream heuristic's smoothing, minimum-duration, and 120s-warmup floors (so a short recorded warmup or short reps are reported as marked) and yields `workout_match.detection_confidence="high"` since the structure is ground truth rather than inferred; the classifier still gates `structure=="intervals"` on `pace_variability` plus a probed structure, so an auto-1km-lapped easy run is not turned into an interval session. A zero-speed standing/autopaused recovery lap is read as rest (the strongest work/rest signal) rather than aborting the lap path, and `compute_confidence` skips its stream-era sanity checks (`work_time_implausibly_high`, `no_warmup_detected`) for `source="recorded_laps"` so ground-truth structure is not contradicted by a low-confidence reason; `upsert_activity` preserves an existing row's recorded `laps` when a lap-less summary payload re-syncs the activity, so a routine manual `POST /api/sync` (summary list endpoint, no laps) does not clobber detail-ingested laps and silently downgrade the lap-sourced structure back to the stream heuristic. The discount-signals stage (`discount_signals.py`) is a deterministic, pipeline-owned annotation marking when HR drift is likely inflated by heat (`average_temp` from `raw_summary`), terrain (`is_hilly`), or the opt-in `UserProfile.stimulant_use` flag, so the coach discounts it rather than reading it as fatigue; it only fires when the drift is actually elevated (above `ELEVATED_DRIFT_THRESHOLD_PCT` 5%, mirroring the `flags.py` fatigue threshold) so a confounder on a negligible-drift run yields no discount instruction (#176); it degrades gracefully and never fabricates a confound. The consolidated-stream-view stage (`stream_view.py`, A2a processed-artifacts layer) runs after metrics and before the `DerivedMetric` upsert: `build_stream_view` produces a bounded (<=60 points), index-aligned, shape-preserving downsample of HR/pace/grade/cadence from the same `streams_dict` (pace derived from velocity and null when stopped, cadence series-mean-normalised to spm), stored on `DerivedMetric.stream_view` (a deferred-load JSON column so the common `activity.metrics` load stays lean and the view is pulled only on demand) and re-derived every analysis; it degrades to null without streams.
The coach layer is `context.py` (assembles the working context — a lean always-present `B baseline` plus the subject activity's `focus payload`, via `build_b_baseline`/`build_focus_payload` composed by `assemble_working_context`, A2b — and flattens it into the pack, byte-identically to the prior one-pass builder) → `llm.py` (Anthropic client) → Pydantic schemas in `app/schemas/coach.py` → `validator.py` (policy gate; `validate_policy` for the structured shape, `validate_message_policy` for the A3 prose shape, both over the shared `check_*` rule bodies) → `service.py` (dispatches on prompt family to `_generate_structured`/`_generate_message`, the A3 prose call going through `llm.generate_coach_message` + `output_contract.py`; caches result in `CoachReport`, with `is_fallback=True` on LLM/parse failure or surviving prose medical-overreach; also stores the A2a exchange digest on `CoachReport.digest` for non-fallback reports via the shared `digest.py` projection, so the stored digest is byte-equal to the longitudinal read). `output_contract.py` (A3) owns the hand-frozen `record_coach_tail` strict-tool JSON, the order-agnostic block parser, and the degrade-not-withhold merge into `CoachMessageReport`. The A2b retrieval seam (`retrieval.py`) pulls A2a's stored processed artifacts on demand: `fetch_stream_view` loads the deferred `DerivedMetric.stream_view` only when an activity is deep-dived (the default report path never loads it), `fetch_prior_digests` reads the stored `CoachReport.digest` (falling back to re-projecting via `digest.py` for pre-A2a rows) for the longitudinal last-exchange memory, `fetch_recent_user_digests` pulls a runner's most recent exchange digests user-scoped (the input the A2c Consolidation job re-grounds the narrative from), and `fetch_prior_commitments` (A2d) pulls the single most recent prior non-fallback exchange's structured `next_steps` + source-activity ref from the stored exchange record, the machine-readable commitments the M7 adherence loop judges later runs against (so `_build_adherence_context` reads through the seam instead of re-querying and carrying the full report body in `context.py`). The deterministic M8 belief write-back (`belief_store.write_back_beliefs`) is provably LLM-free: it derives belief deltas only from the structured `discount_signals` and the M7 adherence outcomes' `label`/`theme`/`overridden`, never from any LLM-written report, next-step rationale, outcome `basis`, or relationship narrative (pinned by `tests/test_writeback_is_llm_free.py`, A2d).
A2c splits durable memory into the existing deterministic-facts half (beliefs/baselines/preferences) and a new LLM `narrative` half: the `coach_narrative` table (one row per user, voice only) holds the bounded relationship story, read into the B baseline by `narrative_store.build_narrative_context` and written by a background `Consolidation` job. After each non-fallback report, `service.py` enqueues `consolidate_narrative_job` (decoupled, right after the M8 belief write-back, no sentinel needed since it is an idempotent single-row rewrite), which calls `consolidation.consolidate_narrative`: it re-derives the narrative from the deterministic facts plus recent exchange digests (never the prior narrative, so re-grounding is structural) via a hardcoded `claude-haiku-4-5` call, and writes ONLY the narrative row (never a belief or baseline, so the deterministic layer stays off the LLM and auditable). The authority boundary is enforced in code (validator rule 6 rejects narrative-as-evidence; the narrative is a separate pack section that never mutates the re-derived `DerivedMetric`) and in prompt (rule 24).
The offline eval harness (M5) under `app/services/coach/eval/` is the deterministic quality gate for the long-horizon learning milestones (M7-M10): it scores each `CoachReport` independently from its stored `report` + `context_pack` against eight rubric assertions (led-with-headline, discounted-inflated-HR (which abstains when a confounder fired on a non-elevated drift, #176), no-medical-overreach reusing validator rule 5, advanced-not-parroted, abstained-on-thin-trend, framed-for-adherence the M10 preference-framing check, load-not-framed-as-intensity the #168 check that the cumulative `effort_score` load number is not narrated as an intensity verdict, and coached-not-caveated the #171 check that when per-rep interval data is present the report coaches it rather than headlining a low detection-confidence caveat or advising the lap button on a recorded-laps session), aggregates a repeatable scorecard scoped to the current `(prompt_id, schema_version)`, and flags regressions across versions; driven by `backend/scripts/eval_coach_reports.py` (the `make eval` / `make eval-selftest` targets). The procedure is documented in `docs/testing/coach-report-eval.md`. The harness scores BOTH output shapes (A3): the rubric extractors branch over the `CoachReportContent | CoachMessageReport` union, the loader parses 2.x rows as `CoachMessageReport` and `make eval` defaults to whichever family the active prompt selects, the scorecard carries a `tail_degraded` counter, and `eval-selftest` validates a good + deliberately-bad fixture for each shape. Under A4 the harness scores the fuller turn only: opener-only rows (an `opener_message` with an empty `message`) are skipped as not-yet-complete and counted in a `skipped_opener_only` scorecard field, never scored.
The notifications layer is a port (`NotifierPort` in `app/services/notifications/port.py`) with `TelegramNotifier` (HTTPS Bot API via `httpx`), `SMTPNotifier` (stdlib `smtplib`), `InMemoryNotifier`, and `NoOpNotifier`. `build_coach_notification` in the package `__init__.py` renders a `Notification` for the active channel, keeping the pipeline channel-agnostic; `email_template.py` renders the email (subject + HTML + plaintext) and `telegram_template.py` renders the Telegram message (title + plaintext body + activity URL); both branch on the report shape via `notifications/_prose.py` to render the A3 prose `message` directly (Telegram truncates at a paragraph boundary under its 4096-char limit) instead of the structured takeaway/next-step lists. `callback_token.py` encodes/decodes the opaque <=64-byte tap tokens carried in `callback_data`, and `TelegramNotifier` additionally exposes `answer_callback` (the tap toast) and `edit_message_reply_markup` (the tapped-button check mark).
The webhook/polling convergence is `app/jobs/process_new_activity.py` (ADR 0004, reshaped by A1/ADR 0011): ingest → analyze → block assignment, then under the two-stage prompt `_schedule_block_complete` (`rq-scheduler` `enqueue_in` at +`BLOCK_GAP_SECONDS` — the grouping gap doubles as the debounce). `block_complete_job` no-ops unless its activity is still the block's last member (idempotency over cancellation; a newer member's check owns the block), the exchange is unopened, and the active prompt is two-stage (a check pending across a rollback flip is a logged no-op, AC6); it then runs the opener stage on the block's PRIMARY activity (`generate_opener` → `Exchange.opened_at` → conditionally `_schedule_fuller_turn` → notify via `Exchange.opener_sent_at`). `fuller_turn_job` runs stage two later (timer-fired or reply-fired), idempotent on `Exchange.fuller_sent_at`, and `maybe_enqueue_fuller_turn` fires it early (on the primary) from the check-in/chat reply paths of ANY block member when the exchange is open — `opened_at` set, `fuller_sent_at` null, within the reply window (ADR 0010). A late activity grouping into an open exchange joins the block (the pending fuller covers the larger event at fire time); into a closed one it starts a new block. The single-shot rollback path is the prior per-activity pipeline, still gated by `Activity.coach_notification_sent_at`.
The frontend is a Next.js 14 App Router project; pages live under `frontend/app/`, reusable UI under `frontend/components/`, and the typed API client and shared types under `frontend/lib/`.
Data flow: Strava API → strava_ingestion → Activity/ActivityStream rows → analysis pipeline → DerivedMetric → coach service → CoachReport → either (a) frontend via `/api/activities/{id}/coach-report`, or (b) notifications via the pipeline job's email send.

## Real-Data Verification

There is no Strava OAuth application for dev or local, so the connect-then-sync path cannot bootstrap data outside production; real-data verification therefore uses one of the two paths below, both documented in `docs/testing/local-seed.md`.
Path 1 (deployed): the production Vercel app (`https://ai-running-coach-eta.vercel.app/`) is publicly reachable and renders real synced data because the frontend injects the backend's HTTP Basic credentials server-side, so browser automation against it verifies any UI or read-path change with no local setup; per-branch preview deployments sit behind Vercel SSO and are not reachable by unauthenticated automation, so pre-merge UI verification uses Path 2.
Preview deployments are not isolated environments: they point at the same single production backend and Postgres/Redis as production, so any write triggered on a preview (sync, destructive migration, delete) mutates production data.
Path 2 (local): `make seed-local` runs `backend/scripts/seed_from_prod.py`, which resets the local schema to the branch's migration head and copies a production snapshot (users, profile, Strava account, baselines, coaching relationship/context/narrative, activities, blocks, exchanges, streams, derived metrics, coach reports, chat, check-ins; activities are inserted with `block_id` nulled and backfilled after blocks land, because the activities/blocks FKs are circular) so the analyze -> coach -> frontend chain runs offline against real data; `SEED_ARGS="--activities N"` bounds the snapshot.
The seed redacts Strava tokens by default so local cannot call Strava and cannot rotate the production refresh token, which means the home page "Sync Now" action fails on a seeded local DB; `SEED_ARGS="--with-live-tokens"` is the opt-in for exercising a real sync and shares the production token.
`seed_from_prod.py` reads the source URL from `SEED_SOURCE_URL` (the `make` target injects Railway's `DATABASE_PUBLIC_URL` via the project token at `~/.railway_token`), only ever reads from the source, and refuses any target URL that is not `localhost`/`127.0.0.1`.
Local verification runs the backend via `uvicorn app.main:app --port 8000` and the frontend via `npm run dev` (port 3000) against the docker-compose Postgres/Redis; `BasicAuthMiddleware` is a no-op locally when `BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD` are unset, so local API calls need no credentials.
